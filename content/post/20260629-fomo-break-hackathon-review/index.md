## 글을 쓰며

2026 SKYSH Hackathon이 끝났다.

대회가 끝난 뒤 깃허브 커밋과 카카오톡 회의 로그를 다시 열어 봤다. 기억만으로 쓰면 내가 한 일을 과장할 수도 있고, 반대로 그날 어떤 판단을 거쳐 제품이 바뀌었는지 놓칠 수도 있다고 생각했다. 실제 기록에는 오전에 처음 방향을 잡은 시점부터 마지막 제출과 발표 준비까지 거의 분 단위로 남아 있었다.

이 글은 그 하루를 처음부터 다시 따라가는 기록이다. 당시 무엇을 알고 있었고, 어떤 선택을 했으며, 각 선택이 다음 작업에 어떤 영향을 주었는지를 순서대로 적는다. 결과와 그에 대한 판단은 실제로 결과가 발표된 지점에서 이야기하려고 한다.

## 참가 동기와 팀 결성

개인적으로는 짧은 시간 안에 제품 방향을 정하고 직접 MVP를 끝까지 끌고 가는 경험이 필요했다. 여러 대회와 MVP 개발 해커톤에 참여한 적은 있었지만, 제품의 방향과 구현을 메인에 가까운 위치에서 책임진 경험은 거의 처음이었다. 내가 다른 사람이 잡은 방향을 구현하는 데서 그치지 않고, 어떤 문제를 풀지부터 시연 가능한 화면까지 이어 붙일 수 있는지 확인하고 싶었다.

팀은 꽤 급하게 꾸렸다. 참가 마감 당일, 공과대학 만화·애니·게임 동아리 애니뮤의 프로그래밍 소모임에서 팀원을 구했다. 갑작스러운 제안이었는데도 `cyanbackpack`, `knowin-kyeong`, `Akebimdru`가 함께해 줬다. 팀 이름은 마감 직전 떠오르는 단어를 그대로 넣었다가 **근고르기**라는 괴상한 이름이 됐다.

네 명의 경험은 꽤 달랐다.

`knowin-kyeong`은 대회 경험이 가장 많았고 AI가 주 분야였지만 MVP 개발은 처음이었다. 나는 여러 대회와 MVP 개발 해커톤에 참여했지만 직접 제품을 총괄한 경험은 거의 처음이었다. `cyanbackpack`과 `Akebimdru`는 컴퓨터공학 지식은 있었지만 개발 프로젝트와 해커톤 참여가 처음이었다.

그래서 역할은 한 사람이 전부 끌고 가기보다, 제한 시간 안에 서로 다른 위험을 나누어 갖는 방식으로 배정했다.

1. `cyanbackpack`: 공개 데이터 수집·검증·재현성
2. `caffeine-fighter`: MVP 총괄·백엔드 API 연결·시연 UX
3. `knowin-kyeong`: ML·KNN·XGBoost·모델 리포트
4. `Akebimdru`: QA·백테스트·컴플라이언스 문구·발표 방향 검수

돌아보면 역할 자체는 대체로 맞았다.

`cyanbackpack`이 맡은 데이터 파이프라인은 해야 할 일이 비교적 명확했다. 어떤 API에서 어떤 데이터를 가져오고, 어떤 형식으로 공유하며, 무엇을 검증할지 정하면 결과물이 보였다. 중요도가 낮다는 뜻은 아니다. 이 작업이 무너지면 점수와 모델이 모두 서로 다른 데이터를 보게 된다. 검증된 CSV와 JSON이 일찍 나온 덕분에 나머지 세 명이 같은 기준에서 움직일 수 있었다.

내가 맡은 축은 맥락 전환이 가장 많았다. 프로젝트 구조와 브랜치 규칙을 정하다가 백엔드 응답을 맞추고, 다시 프론트엔드로 넘어가 시연 흐름을 고쳐야 했다. 마지막에는 발표자료와 영상도 같은 제품을 설명하게 만들어야 했다. 메인에 가까운 위치에 선 것이 처음이어서 내가 병목을 만든 순간도 있었다.

`knowin-kyeong`에게는 대회 경험과 AI 역량이 있었다. 우리가 직접 만들 FOMO 지표와 과거 패턴, 시계열 모델을 맡기기에 가장 자연스러운 사람이었다.

`Akebimdru`의 역할은 개발 속도만 보면 눈에 덜 띌 수 있다. 하지만 금융 주제에서는 표현 하나가 제품의 성격을 바꾼다. “오를 가능성이 있다”와 “과거에 이런 구간이 있었다”는 전혀 다른 말이다. 직접적인 행동 유도와 수익 보장 표현을 걷어내고, 백테스트와 발표 문구가 투자 추천처럼 보이지 않는지 확인하는 사람이 필요했다.

## 준비 과정

처음부터 준비가 잘된 팀은 아니었다.

6월 22일부터 24일까지 카카오톡에는 “주제 관련 메일 받은 거 있나요”, “주제를 모르겠어서요”, “어렵네요” 같은 말이 남아 있다. 25일 새벽에야 미리 시작할 수 있다는 이야기가 나왔고, 초기 아이디어도 패닉셀이나 FOMO 같은 감정 투자를 막는다는 정도였다. 개인의 감정을 직접 입력받을지, 초보자에게 어떤 정보를 보여줄지, 정보 비대칭을 어떻게 줄일지도 정해지지 않았다.

방향이 잡힌 것은 6월 27일 밤이었다. 다른 팀도 비슷한 주제를 고를 수 있으니 차별점이 필요했다. 개인의 감정 데이터를 받는 대신 업비트 공개 데이터로 시장 전체의 과열 상태를 관찰하고, 사용자가 행동하기 전에 멈추게 하기로 했다. **FOMO Break**라는 이름도 이때 나왔다.

대회 당일 오전 9시 14분경에는 MVP를 세 기능으로 좁혔다.

1. FOMO Score
2. Historical Mirror
3. Decision Pause

10시 20분에는 점수 산식, 데이터 크롤링, 패턴·시계열 분석, 통계 분석, 프론트엔드 순으로 작업하기로 했다. 그때 정한 순서는 거의 그대로 하루의 작업 순서가 됐다.

### 최종적으로 만들고자 한 FOMO Break

세부 기능이 언제 붙고 어떻게 바뀌었는지는 뒤의 시간순 기록에서 설명한다. 먼저 하루 동안 완성하려고 한 제품의 전체 모습을 정리하면 다음과 같다.

FOMO Break는 업비트 공개 데이터를 바탕으로 시장의 공포와 탐욕 상태를 관찰하고, 초보 사용자가 감정적으로 매수·매도하려는 순간 한 번 멈추게 하는 MVP다.

흔한 코인 예측기나 매수·매도 신호를 만들고 싶지는 않았다. 오히려 정반대였다.

> 더 빠르게 결정하게 하는 서비스가 아니라, 더 천천히 판단하게 하는 서비스.

사용자가 밟는 순서는 공개 데이터 확인, FOMO Score, 과거 유사 구간, Decision Pause였다. 핵심은 마지막 단계였다.

1. 업비트 공개 캔들 데이터를 수집하고 오류를 검증한다.
2. 8개 지표로 FOMO Score를 계산한다.
3. Historical Mirror와 KNN Mirror로 닮은 과거 구간을 보여준다.
4. 가상 매수·매도 시도는 실제 주문으로 보내지 않고 Decision Pause로 넘긴다.
5. 사용자가 자기 판단의 근거가 정보인지 감정인지 직접 확인한다.

이 과정에서 지킬 선도 정했다.

- 사용자 API Key나 Secret Key를 받지 않는다.
- 개인정보를 수집하지 않는다.
- 투자 추천·자문·수익 보장 문구를 쓰지 않는다.
- 계산 결과는 시장 상태 관찰과 과거 참고 사례로만 설명한다.

FOMO Score에는 가격 모멘텀, 가격 강도, 상승일 거래량 비율, CLV 매수 압력, RSI, 변동성 역수, 거래량 모멘텀과 연속 상승일을 사용했다. 특히 거래량 모멘텀과 연속 상승일에 높은 가중치를 뒀다. 초보자가 “지금 안 타면 놓칠 것 같다”고 느끼는 장면이 대개 거래량이 급증하고 며칠 연속 오르는 구간과 맞닿아 있다고 봤기 때문이다.

산식은 CNN Fear & Greed Index를 출발점으로 참고하되, 암호화폐 공개 데이터와 초보 사용자의 행동에 맞게 다시 구성했다. 기존 지표의 이름만 가져다 쓴 것이 아니라, 우리가 실제로 수집할 수 있는 값과 제품에서 설명할 수 있는 값으로 좁혔다.

점수를 만드는 일만큼 그 점수를 예측처럼 보이지 않게 하는 일이 중요했다. FOMO Score는 가격 예측값이 아니라 시장 심리 관찰값이었다.

Historical Mirror도 같은 이유로 만들었다. 현재와 점수가 비슷했던 과거 구간을 보여주되, 그 뒤의 수익률을 미래 예측처럼 말하지 않았다. KNN Mirror는 점수 하나만 비교하는 대신 1일 변화율, 거래량 비율과 RSI까지 함께 봤다. 현재 시장이 과거의 어느 장면과 닮았는지를 참고하게 할 뿐, 그때와 같은 결과가 나온다고 약속하지 않았다.

프론트엔드에서는 이 기능들을 **Judgment Firewall**이라는 흐름으로 묶기로 했다. 사용자가 가상 매수나 매도를 눌러도 주문은 전송되지 않는다. 표시용 현재가와 시장 상태, 과거 구간과 오차 범위를 보고 체크리스트로 자기 판단의 근거를 확인하게 했다. 기능 이름은 거창하지만 하고 싶었던 일은 단순했다. 흥분한 상태에서 버튼부터 누르는 시간을 몇 분이라도 늦추는 것이었다.

이제 문제는 이 아이디어를 하루 안에 실제 화면으로 만드는 일이었다.

## 대회 중 경과

### 09:00–12:00 — 데이터와 백엔드부터 잠그다

오전에는 행사장 도착, 깃허브 권한 설정, API 조사와 MVP 기능 정리가 한꺼번에 진행됐다. 10시 30분경 역할을 나눈 뒤부터 팀은 병렬로 움직였다.

깃허브 기록상 11시 9분에 프로젝트 구조 초기화 커밋이 올라갔고, 11시 21분에는 README가 정리됐다. 11시 38분에는 Historical Mirror API, 11시 46분에는 관련 테스트가 추가됐다.

나는 프로젝트 구조와 기준 브랜치를 잡고 Historical Mirror와 `/api/mvp-overview`를 붙였다. 이후 KNN Mirror와 비교할 수 있도록 응답 계약을 맞추고, API 파라미터 검증과 문서를 정리했다.

`cyanbackpack`은 업비트 공개 캔들 수집과 검증을 맡았다. 실제로 공유한 데이터는 KRW-BTC, KRW-ETH, KRW-XRP 각각 565행, 총 1,695행이었고 missing dates, duplicate dates, OHLC errors, value errors는 모두 0이었다. 11시 40분경에는 업비트 클라이언트 확장과 테스트 20개 통과도 공유됐다.

해커톤에서 데이터가 있다는 것과, 모두가 같은 검증된 데이터를 보고 다시 실행할 수 있다는 것은 전혀 다르다. DB 파일은 커밋하지 않고 `data/upbit_candles_snapshot.csv`와 `data/crawl_report.json`으로 넘기기로 했다. DB 파일을 직접 공유하면 충돌이 생기고 누가 어느 시점의 데이터를 보는지 알기 어렵다. CSV와 JSON으로 고정한 덕분에 뒤의 점수와 Mirror, ML 리포트가 같은 기준 위에서 돌아갔다.

오전 안에 눈에 보이는 화면이 완성된 것은 아니었다. 그래도 데이터를 가져오고, 검증하고, 점수를 계산하며 과거 구간을 찾는 백엔드의 뼈대는 세웠다.

### 12:00–15:00 — Mirror와 모델을 제품 안에 넣다

정오 이후에는 협업 규칙부터 정리했다. 공용 기준 브랜치는 `feature/historical-mirror-polish`였고 각자 작업 브랜치를 만든 뒤 PR을 올리기로 했다. force push와 공용 브랜치 직접 커밋도 금지했다.

12시 35분부터 50분 사이에는 크롤링 PR과 데이터 export가 정리됐다. 오후 1시 25분경에는 Historical Mirror와 KNN Mirror를 같은 화면에서 비교할 수 있도록 응답 구조를 맞췄다. `/api/mvp-overview`에서는 KNN을 기본 실행하지 않고 `include_knn=true`일 때만 포함하도록 했다.

오후 1시 22분 이후부터는 ML 작업도 빠르게 늘었다. 깃허브에는 `feat: add KNN mirror and FOMO score forecast`, `KNN k-optimization`, `XGBoost FOMO Score training`, `expanding-window backtest`와 `feat(viz): final 7 graphs — ensemble redrawn as stitched timeline` 같은 커밋이 남아 있다.

`Akebimdru` 쪽에서도 11시 52분 `feat: add FOMO score backtest and quality report`, 13시 27분 `feat: expand FOMO score sensitivity backtest`가 이어졌다. 모델을 붙이는 것과 별개로 점수 산식의 민감도와 품질, 어떤 표현까지 안전한지를 확인하는 축이었다.

Historical Mirror는 현재 FOMO Score와 가까운 과거 구간을 찾고, KNN Mirror는 1일 변화율·거래량 비율·RSI 같은 피처까지 비교했다. XGBoost와 expanding-window backtest도 FOMO Score의 참고 흐름을 만들기 위해 붙였다.

여기서 개발 중 예측 결과가 시점과 모델에 따라 크게 흔들렸다. 초기 일부 실험에서는 baseline보다 좋지 않은 구간도 있었고, KNN 이웃이 너무 최근 날짜에 몰릴 위험도 있었다. 최종 저장소에서는 XGBoost가 세 마켓 모두 persistence baseline보다 나은 구간을 확보했지만, 대회 중에는 그 결과를 일반적인 가격 예측 성능으로 확대해 말할 근거가 부족했다.

이 지점에서 선택해야 했다. “AI가 미래를 예측한다”고 포장하면 발표에서는 더 화려해 보일 수 있었다. 대신 성능이 애매한 값을 강한 예측으로 말하게 된다.

우리는 그렇게 하지 않았다.

모델을 정답을 맞히는 예측기가 아니라 과거 참고와 보조 관찰 리포트로 내렸다. 숫자를 더 강하게 말하는 것보다 제품이 처음 정한 선을 지키는 편이 맞았다. 아쉬움이 없는 결정은 아니었지만, 지금 돌아봐도 같은 선택을 할 것 같다.

### 15:00–18:30 — 프론트엔드가 가장 큰 병목이 되다

오후 3시 34분경, 프론트엔드는 사실상 placeholder에 가깝고 발표에서 보여줄 화면이 없다는 평가를 받았다. FOMO Score 게이지도, Historical Mirror 테이블도, Decision Pause 화면도 제대로 보이지 않았다.

그때부터 나는 거의 프론트엔드에 붙어 있었다.

깃허브에는 15시 22분 `add mvp frontend dashboard`, 15시 31분 `enhance frontend decision experience`, 16시 `fix frontend api integration`, 16시 13분 `integrate public ticker snapshot`, 16시 28분 `add frontend judgment firewall demo`가 연달아 남아 있다. 이때부터 FOMO Break가 API 묶음에서 실제 제품 화면으로 바뀌기 시작했다.

한 번에 좋아지지는 않았다. 가로 폭이 부족해 글자가 잘렸고, 체크를 해제할 수 없었으며, 체크하면 다음 단계로 자동으로 넘어갔다. 판단 준비도와 실제 Decision Pause 사이의 거리도 멀었다. 차트와 카드와 설명을 다 넣으니 사용자가 무엇을 해야 하는지 보이지 않았다.

> 새로운 사용자가 전혀 적응하지 못한다.

맞는 지적이었다.

처음에는 차트, 카드, 설명과 리포트를 한 화면에 모두 보여주려 했다. 정보량을 기술적 완성도로 착각한 셈이다. 그래서 상세 차트와 KNN, 백테스트는 보고서 영역으로 내리고, 기본 화면에는 가상 매수·매도 시도, 공개 데이터 확인, Decision Pause, 판단 근거 정리만 남겼다.

많은 서비스가 사용자를 더 빠르게 매수·매도 화면으로 보내려고 한다면, 우리는 그 길목에서 일부러 한 번 멈추게 하고 싶었다. 점수나 모델보다 이 사용자 흐름이 먼저 보여야 했다.

커밋명에는 당시의 싸움이 그대로 남아 있다.

- `prevent virtual order panel overflow`
- `connect decision pause transition`
- `tighten decision pause demo layout`
- `prevent compact demo text clipping`
- `shorten compact demo labels`
- `simplify demo microcopy`
- `simplify guided demo UI`
- `rebuild guided self-check UI`

거창한 새 기능은 거의 없다. 화면이 넘치지 않게 하고, 잘린 글자를 줄이고, 버튼을 누른 다음 단계가 제대로 이어지게 하는 수정들이다. 오후 4시 30분부터 6시 30분까지는 제품을 더 크게 만드는 시간이 아니라, 겨우 제품처럼 보이고 실제로 시연되게 만드는 시간이었다.

현재 저장소에서 내 두 author 표기를 합치면 merge commit을 포함해 90개가 넘는 커밋이 남아 있다. 프론트엔드 대부분과 시연 영상, 백엔드 상당 부분, 발표 직전 폴리싱이 내 손을 거쳤다. 숫자를 자랑하려는 것이 아니다. 내가 이 프로젝트를 대충 굴린 것은 아니라는 사실을 남기고 싶다.

문제는 데이터, 모델과 검수 결과가 쌓이는 동안 발표 화면을 만드는 책임이 후반에 내 쪽으로 너무 많이 몰렸다는 점이었다. 역할 배정은 맞았지만 각 역할의 결과가 화면에서 어떻게 보이는지 함께 확인하는 구조는 없었다.

### 18:30 이후 — 제출과 발표 준비

저녁 6시 30분 이후에는 제출물이 현실로 다가왔다. 필요한 것은 5분 발표용 PDF, 링크나 실행 파일로 배포할 수 있는 결과물, 2분 이내·1GB 이하의 시연 영상이었다.

중간 심사 답변도 한 문장으로 정리했다.

> FOMO Break는 투자 추천 앱이 아니라, 사용자가 감정적으로 매수·매도하려는 순간을 가상으로 포착해 실제 주문 경로를 차단하고, Upbit 공개 데이터 기반의 시장 상태·과거 유사 구간·오차 범위를 확인한 뒤 Decision Pause로 자기 점검하게 만드는 판단 방화벽입니다.

7시 45분에는 발표자료 PDF가 공유됐다. 8시 20분대에는 발표 분담과 대본이 오갔다. 실제 발표 기회가 올 것이라고 생각해 시연과 마지막 문장까지 준비했다. 끝까지 버티려고 몬스터도 마셨다.

화면만 보면 코인 점수 앱으로 오해하기 쉬웠기 때문에 발표가 특히 중요했다. 왜 실제 주문을 막았는지, 왜 모델을 예측기가 아니라 참고 자료로 낮췄는지, Decision Pause가 기존 서비스와 무엇이 다른지를 말로 이어야 했다. 우리는 그 설명을 할 준비까지 마쳤다.

8시가 지나면서 분위기가 이상해졌다. 최종 발표 팀이 이미 따로 불리고 있는 것 같다는 이야기가 나왔다. 8시 34분 카카오톡에는 “비상”이라는 말이 남아 있다.

그때까지는 정확한 결과를 알지 못했다.

## 결과

우리 팀은 최종 발표 대상에 포함되지 않았다. 수상도 하지 못했다.

9시 31분에는 “다들 수고했음”, “좋은 경험이었음” 같은 말을 주고받고 끝났다. 발표할 줄 알고 카페인을 때려 넣은 탓에 잠도 오지 않았고, 다음 날 강의와 바로 이어진 다른 대회 일정에도 그대로 문제가 생겼다. 결과가 나오기 전까지 대본과 기능을 붙잡은 비용을 온몸으로 치른 뒤라 더 허탈했다.

개인적으로 가장 아쉬운 부분은 발표 기회를 얻지 못했다는 점이었다. FOMO Break는 설명이 필요한 제품이었다. 단순히 화면만 보면 코인 점수 앱처럼 보일 수 있지만, 실제 의도는 그 반대였다. 매매를 추천하지 않기 위해 표현을 덜어냈고, 사용자의 행동을 빠르게 만들기보다 느리게 만드는 UX를 설계했다.

그 차이는 발표에서 설명해야 전달된다. 우리는 그 기회를 얻지 못했다.

### 내가 결과를 납득하지 못한 이유

여기서부터는 조금 공격적으로 들려도 어쩔 수 없다. 나는 아직도 이 결과를 완전히 납득하지 못한다.

대회 진행과 공간, 분위기에는 크게 불만이 없었다. 내가 문제라고 생각한 것은 심사였다. 좋은 행사를 만들었더라도 마지막 평가가 전문성과 설명 책임을 보여주지 못하면 참가자에게 오래 남는 것은 결국 그 지점이다.

내가 보기에는 5개 학교에서 한 명씩 심사위원을 맡은 구조였던 것 같다. 정확한 내부 사정은 모른다. 적어도 내가 제대로 대화가 된다고 느낀 사람은 서울대 측 심사위원이었다. 그날 밤 순위를 물었고, 우리 팀이 딱 중간 정도였다는 답을 들었다. 무엇이 결정적인 문제였는지 물어도 선명한 설명은 없었다. 내가 확인한 약점은 프론트엔드 완성도와 팀 이름 정도였고, 들은 설명은 주제가 겹쳤고 평가 기준이 서로 달랐다는 쪽에 가까웠다.

그 말은 위로가 되지 않았다. 같은 주제라도 어떤 관점으로 풀었고 어디까지 구현했는지를 보는 것이 해커톤이라고 생각한다. 우리는 코인 점수만 보여주지 않았다. 매수·매도 신호를 피했고, 공개 데이터만 사용했으며, 과거 유사 구간과 Decision Pause를 한 흐름으로 만들었다.

그 차이가 보이지 않았다면 심사가 제대로 작동했다고 보기 어렵다. 운영은 해커톤이었는데 심사는 아이디어 발표회와 인기투표 사이 어딘가에 걸쳐 있었던 것처럼 느껴졌다.

이 정도면 꽤 돌려 말한 것이다.

집에 가는 길에는 친구에게 “내가 버스 탄 해커톤은 다 잘되고, 내가 버스 운전한 해커톤은 다 망한다”고 보냈다. “나는 아직 능력이 부족한가봄”이라고도 했다. 하지만 너무 공격적으로 보이지 않으려고 한 말에 가까웠다.

솔직한 속내는 달랐다. 나는 내 능력을 의심하지 않았다. 프론트엔드와 영상, 백엔드 상당 부분을 붙잡고 내 이름으로 90개가 넘는 커밋 기록을 남긴 프로젝트가 발표 한 번 없이 중간 정도로 처리된 심사 구조를 의심했다.

같은 팀의 ML 담당이었던 `knowin-kyeong`은 [자신의 후기](https://knowin-kyeong.github.io/%EB%8C%80%ED%9A%8C%20%ED%9B%84%EA%B8%B0/fomo-break-hackathon-review/)에서 이 결과를 다르게 복기했다. 사전 준비가 부족했고, 정량 모델에 집중하는 동안 해커톤이 평가하는 문제 정의와 스토리텔링을 놓쳤으며, 다른 발표팀의 결과물을 본 뒤에는 탈락을 납득했다고 썼다.

그 분석도 틀렸다고 생각하지 않는다. 그는 ML 파트에서 모델의 한계와 다른 팀 발표를 중심으로 대회를 봤고, 나는 제품 전체의 구현량과 심사위원에게 직접 들은 설명을 중심으로 결과를 봤다. 같은 팀에서도 담당한 영역과 결과를 접한 방식에 따라 판단이 달라질 수 있다. 그의 오답노트와 내가 가진 문제의식은 동시에 읽을 필요가 있다.

물론 내 잘못도 있었다. 발표 가능한 UI를 더 빨리 만들었어야 했고, 팀 이름도 덜 이상하게 지었어야 했다. 제품의 차별점은 심사자가 놓치기 어렵게 더 노골적으로 포장했어야 했다. 그렇다고 우리가 발표조차 할 수준이 아니었다는 판단에는 동의하지 않는다. 백엔드와 데이터 파이프라인, 모델 리포트, Decision Pause 설계를 놓고 보면 적어도 기술적 깊이에서 밀릴 프로젝트는 아니었다고 생각한다.

대상을 탔어도 이상하지 않았을 만큼 진지하게 만들었고, 최소한 발표 한 번은 해볼 만한 결과물이었다. 이것은 객관적인 순위를 단정하는 말이 아니라, 전체 구현과 기록을 다시 본 지금의 내 판단이다.

## 오답노트

결과를 납득하지 못한다고 해서 내가 고칠 부분까지 없는 것은 아니다. 내가 바꿀 수 있었던 것과 직접 바꾸기 어려웠던 것을 나누어 봤다.

### 내가 바꿀 수 있었던 것

- 첫 세 시간 안에 빈 데이터로라도 발표 가능한 최소 화면을 만들었어야 했다.
- 데이터·모델·QA 담당도 중간부터 시연 화면을 함께 검수하게 했어야 했다.
- “우리가 하지 않는 것”과 Decision Pause의 차별점을 첫 화면에서 더 강하게 보여줬어야 했다.
- 모델과 리포트를 늘리기 전에 사용자가 밟을 한 가지 흐름부터 잠갔어야 했다.
- 심사 기준에 맞는 한 문장과 시연 순서를 더 일찍 확정했어야 했다.
- 팀 이름처럼 제품 외부에서 감점될 수 있는 요소도 가볍게 보지 말았어야 했다.

가장 큰 실수는 프론트엔드를 작업 순서의 맨 마지막에 둔 것이다. 데이터와 산식이 있어야 화면을 만들 수 있다는 논리는 맞았다. 하지만 해커톤에서는 완성된 데이터가 없어도 사용자가 무엇을 누르고 무엇을 보게 될지부터 보여줘야 한다. 우리는 제품의 머리부터 만들고 얼굴은 너무 늦게 보기 시작했다.

좋은 제품을 만드는 것과 평가 구조 안에서 그 장점을 바로 알아보게 만드는 것은 다른 일이다. 이번에는 후자를 너무 늦게 챙겼다.

다음에는 첫 화면부터 만든다.

### 내가 직접 바꾸기 어려웠던 것

- 최종 발표팀을 고르는 심사위원의 전문 분야와 평가 기준
- 짧은 평가 시간 안에 각 저장소와 구현을 얼마나 깊게 확인했는지
- 비슷한 주제를 선택한 팀이 여러 개였다는 사실
- 발표 기회를 받지 못하면 제품의 의도를 설명할 방법이 거의 없었던 구조

이 부분은 내가 더 열심히 구현한다고 직접 바뀌지 않는다. 대신 다음 대회를 고를 때 심사위원의 전문성과 평가 방식, 중간 피드백과 최종 발표 기회가 어떻게 주어지는지를 더 먼저 확인할 수는 있다.

참가자의 시간과 노동을 가져가는 대회라면 결과를 납득시킬 평가와 피드백도 책임져야 한다. 운영이 괜찮았다는 사실과 심사가 아쉬웠다는 사실은 동시에 성립한다.

내 기억에 더 오래 남은 것은 후자다.

- 판단 근거 정리 화면
- 발표자료와 시연 영상

당일 처음 공유한 데이터는 1,695행이었지만, 이후 저장소에서 장기 백테스트용 데이터를 세 마켓 각각 2,200일, 총 6,600행까지 확장했다. 최종 기록에는 전체 테스트도 `120 passed, 5 skipped`로 남아 있다. 행사장에서 한 번 돌아간 데모로 끝내지 않고, 대회 뒤에도 다시 실행하고 검증할 수 있는 프로젝트 형태로 정리했다.

네 명의 역할도 실제 결과로 이어졌다. 검증된 데이터가 있었고, 모델의 한계를 확인한 뒤 제품 안에서 위치를 조정했으며, 투자 추천처럼 보이지 않게 문구를 통제했다. 갑자기 모인 팀이 하루 만에 이 정도까지 간 데에는 각자가 맡은 축을 놓지 않은 영향이 컸다. 혼자였다면 백엔드와 화면은 만들었을지 몰라도 검증 데이터와 모델 리포트, 규정 문구까지 한꺼번에 갖추지는 못했을 것이다.

그중에서도 내가 가장 좋게 보는 것은 기능 수가 아니다. 끝까지 투자 추천으로 방향을 틀지 않았다는 점이다. 우리는 사용자 API Key와 개인정보를 받지 않았고, 실거래를 보내지 않았으며, 가격을 맞힌다고 말하지 않았다.

대신 한 가지를 물었다.

> 지금 이 판단은 정보에 기반한 것인가, 감정에 끌려가는 것인가?

나는 FOMO Break가 괜찮은 제품이었다고 생각한다.

아니, 꽤 좋은 제품이었다고 생각한다.

내가 처음으로 제품 방향과 구현을 중심에서 끌고 갔고, 마지막까지 실제 시연 가능한 형태로 완주했다는 점도 남았다. 결과와 별개로 이 경험 이후에는 백엔드, 프론트엔드와 발표를 따로 보지 않고 하나의 사용자 흐름으로 관리해야 한다는 기준이 생겼다.

## 앞으로

다음 해커톤에서는 시작부터 세 가지를 다르게 할 것이다.

첫째, 첫 화면과 5분 시연 흐름을 가장 먼저 만든다. 데이터와 모델은 그 흐름에 필요한 만큼만 붙이고, 각 담당자가 자기 결과가 화면에서 어떻게 보이는지 함께 책임지게 한다.

둘째, 기술적으로 하고 싶은 일과 심사에서 알아볼 수 있는 일을 처음부터 구분한다. 차별점은 설명을 듣고 나서야 보이는 장점이 아니라, 첫 화면과 첫 문장에서 보이는 장점이어야 한다.

셋째, 아무 대회에나 나가지는 않을 생각이다. 심사위원이 실제로 제품과 기술을 평가할 수 있는지, 결과에 대한 피드백이 있는지, 참가자의 작업을 볼 시간이 마련되어 있는지를 먼저 확인하고 싶다.

이번에는 보여주지 못했다.
