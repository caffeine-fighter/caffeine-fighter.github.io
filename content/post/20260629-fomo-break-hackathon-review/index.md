2026 SKYSH Hackathon이 끝났다.

결과부터 말하면, 우리 팀 **근고르기**는 수상하지 못했다. 더 정확히는 최종 발표 기회도 얻지 못했다. 솔직히 많이 아쉬웠다. 단순히 떨어져서가 아니라, 우리가 만든 결과물이 생각보다 꽤 괜찮았고 심사 기준이었던 창의성, 완성도, 기술성, 발전성에 나름 정면으로 답하고 있었다고 생각했기 때문이다.

그래서 이 글은 "억울했다"는 감정만 남기기 위한 글은 아니다. 물론 억울했다. 하지만 그보다 더 오래 남겨두고 싶은 건 우리가 어떤 문제를 잡았고, 어떻게 역할을 나눴고, 하루 동안 어떤 순서로 제품을 완성했는지다.

깃허브 커밋 기록과 카카오톡 회의 로그를 다시 보니, 이 프로젝트는 생각보다 더 선명한 흐름을 갖고 있었다.

## FOMO Break

우리가 만든 제품은 **FOMO Break**다.

FOMO Break는 업비트 공개 데이터를 기반으로 시장의 공포와 탐욕 상태를 관찰하고, 초보 사용자가 감정적인 판단을 하기 전에 자기 점검을 하도록 돕는 MVP다.

처음부터 방향은 명확했다.

- 업비트 공개 API만 사용한다.
- 사용자 API Key나 Secret Key를 받지 않는다.
- 개인정보를 수집하지 않는다.
- 투자 추천, 투자 자문, 수익 보장 문구를 쓰지 않는다.
- 결과는 "시장 상태 관찰", "과거 참고 사례", "자기 점검"의 언어로 설명한다.

우리가 피하고 싶었던 건 흔한 "매수/매도 신호"였다. 해커톤에서 금융이나 코인 주제를 잡으면 예측 모델, 자동 매매, 추천 서비스 쪽으로 가기 쉽다. 하지만 우리는 정반대의 방향을 잡았다.

> 더 빠르게 결정하게 하는 서비스가 아니라, 더 천천히 판단하게 하는 서비스.

그게 FOMO Break의 출발점이었다.

핵심 흐름은 다음과 같았다.

1. 업비트 공개 캔들 데이터를 수집한다.
2. 결측, 중복, OHLC 오류, 값 오류를 검증한다.
3. 8개 지표를 이용해 FOMO Score를 계산한다.
4. Historical Mirror와 KNN Mirror로 닮은 과거 구간을 보여준다.
5. 사용자가 가상 매수/매도 행동을 하려는 순간 Decision Pause로 넘긴다.
6. 마지막에 자기 판단의 근거를 정리하게 한다.

말하자면 단순 대시보드가 아니라, **공개 데이터 -> 심리 점수 -> 과거 참고 -> 행동 전 자기 점검**으로 이어지는 관찰 파이프라인을 만든 셈이다.

## 팀 근고르기

팀원 표기는 전부 핸들로만 남긴다. 우리 팀은 네 명의 경험치가 꽤 달랐다.

`knowin-kyeong`은 대회 경험이 가장 많았고 AI 쪽이 주 분야였지만, MVP 개발은 처음이었다. 나는 MVP 개발 해커톤을 포함해 여러 대회에 참여해 본 적은 있었지만, 직접 메인으로 제품 방향과 구현을 끌고 간 경험은 이번이 거의 처음이었다. `cyanbackpack`과 `akebimdru`는 컴퓨터공학적 지식은 어느 정도 있었지만, 개발 프로젝트와 해커톤 참여는 처음이었다.

그래서 역할 배정은 "경험 많은 사람이 전부 끌고 간다"가 아니라, 제한 시간 안에 리스크를 나눠 갖는 쪽에 가까웠다.

1. `cyanbackpack`: 공개 데이터 수집, 검증, 재현성
2. `caffeine-fighter`: MVP 총괄, 백엔드 API 연결, 시연 UX
3. `knowin-kyeong`: ML, KNN, XGBoost, 모델 리포트
4. `akebimdru`: QA, 백테스트, 컴플라이언스 문구, 발표 방향 검수

돌아보면 이 배정은 대체로 적합했다.

1번 역할은 처음 해커톤에 참여하는 팀원에게 맡기기 좋은 축이었다. 물론 중요도가 낮아서가 아니다. 데이터 파이프라인은 제품 전체의 기반이지만, 해야 할 일이 비교적 명확했다. 어떤 API에서 어떤 데이터를 가져오고, 어떤 형식으로 넘기고, 어떤 검증 리포트를 만들지 정하면 결과물이 선명하게 나온다. `cyanbackpack`이 이 역할을 맡은 덕분에 팀 전체가 같은 CSV/JSON 기준을 보고 움직일 수 있었다.

2번 역할은 가장 리스크가 컸다. MVP 총괄은 백엔드, API 계약, 프론트엔드, 발표 흐름을 계속 이어 붙여야 해서 맥락 전환이 많다. 내가 여러 대회와 MVP 개발 해커톤을 경험해 본 적이 있었기 때문에 이 역할을 맡는 건 자연스러웠지만, 동시에 처음으로 메인에 가까운 위치에 섰기 때문에 병목도 많이 만들었다. 특히 발표 가능한 UI를 너무 늦게 본격화한 점은 다음에는 고쳐야 할 부분이다.

3번 역할은 가장 잘 맞았다. `knowin-kyeong`은 대회 경험과 AI 역량이 있었고, 우리 제품에도 KNN Mirror, XGBoost, backtest 같은 모델 기반 설명이 필요했다. 다만 MVP 개발은 처음이었기 때문에 모델을 제품 전면의 "예측기"로 밀어붙이기보다는, 과거 참고와 보조 관찰 리포트로 위치를 낮춘 판단이 좋았다. 이 덕분에 AI 파트가 제품의 방향을 흔들기보다 설득력을 보태는 쪽으로 붙었다.

4번 역할도 적합했다. `akebimdru`는 첫 해커톤이었지만, 이 프로젝트는 기능보다 표현의 안전성이 중요한 주제였다. 투자 추천처럼 보이지 않게 만들고, 결과를 "시장 상태 관찰"과 "과거 참고"로 설명하게 하는 검수는 제품의 신뢰도와 발표 방향에 직접 연결됐다. 개발 속도를 올리는 역할과는 다르지만, 금융 주제에서는 이 경계선을 잡아주는 사람이 꼭 필요했다.

아쉬운 점이 있다면, 1번과 4번 역할을 더 일찍 프론트엔드 시연 흐름에도 연결했어야 한다는 것이다. 역할 배정 자체는 맞았지만, 시연 가능한 화면을 만드는 책임이 후반에 2번으로 너무 몰렸다. 다음에 같은 팀으로 다시 한다면 데이터, 모델, QA가 모두 "발표 화면에서 어떻게 보이는지"를 더 일찍 같이 확인하는 구조를 만들고 싶다.

### 1번. `cyanbackpack`

`cyanbackpack`은 데이터 파이프라인과 재현성 쪽을 맡았다.

대회 전날 밤부터 "FOMO Break"라는 방향이 나오기 시작했고, 곧이어 개인 감정을 입력받는 서비스가 아니라 업비트 공개 체결 데이터로 시장 전체의 FOMO나 공포·탐욕 상태를 관찰하는 쪽으로 제품의 축이 잡혔다. 이게 중요했다. 개인의 감정 데이터를 받지 않고 공개 시장 데이터만으로 흐름을 보겠다는 원칙이 생긴 순간이었기 때문이다.

대회 당일에는 업비트 공개 캔들 데이터 수집, CSV/JSON export, crawl report 정리, DB 파일을 커밋하지 않는 규칙, 검증 결과 공유까지 맡았다. 실제 공유된 데이터는 KRW-BTC, KRW-ETH, KRW-XRP 각 565 rows, 총 1695 rows였고, missing_dates, duplicate_dates, ohlc_errors, value_errors 모두 0이었다.

해커톤에서 데이터가 "있다"와 "검증되어 있고 재현 가능하다"는 전혀 다르다. 이 기반이 있었기 때문에 뒤의 FOMO Score, Mirror, ML 리포트가 같은 기준 위에서 돌아갈 수 있었다.

### 2번. `caffeine-fighter`

나는 MVP 총괄과 백엔드 API 연결, Historical Mirror, Decision Pause, 프론트엔드 시연 UX를 맡았다.

초반에는 프로젝트 구조를 잡고, 기준 브랜치와 작업 브랜치를 정리하고, Historical Mirror API와 `/api/mvp-overview`를 붙였다. 이후 KNN Mirror와 비교 가능한 응답 계약을 맞추고, API 파라미터 검증과 문서 정리를 했다.

후반에는 거의 프론트엔드에 붙어 있었다. 처음에는 `frontend/`가 사실상 placeholder에 가까웠고, 중간 피드백에서도 "발표에서 화면을 보여줄 수 없는 상태"라는 평가가 나왔다. 그래서 마지막 몇 시간은 FOMO Score 게이지, 공개 데이터 확인, 가상 주문 시도, Decision Pause, 판단 근거 정리까지 한 화면에서 시연 가능한 흐름으로 만드는 데 썼다.

15시 22분 `add mvp frontend dashboard` 이후부터 20시대까지 프론트엔드 관련 커밋이 거의 연속으로 이어진다. 기능을 새로 늘렸다기보다는, 실제 시연이 가능한 제품처럼 보이게 만들기 위한 끝없는 다듬기였다.

### 3번. `knowin-kyeong`

`knowin-kyeong`은 ML, KNN, XGBoost, 모델 리포트 쪽을 맡았다.

초기 회의에서 데이터가 있으면 하루 만에 CatBoost나 XGBoost 같은 모델을 붙여볼 수 있다는 이야기가 나왔고, 실제로 대회 중반부터 KNN Mirror, FOMO Score forecast, XGBoost 학습, expanding-window backtest, 시각화 리포트가 빠르게 붙었다.

깃허브 기록에도 `feat: add KNN mirror and FOMO score forecast`, `KNN k-optimization`, `XGBoost FOMO Score training`, `expanding-window backtest`, `final graphs` 같은 커밋이 남아 있다.

중요한 건 이 모델 파트를 최종 제품에서 "예측"으로 밀지 않았다는 점이다. 성능이 애매하거나 노이즈가 큰 부분은 MVP 전면에 내세우지 않고, "과거 참고 사례"와 "보조 관찰 렌즈"로 설명하려고 했다. 이 판단은 제품의 안전한 방향과도 맞았다.

### 4번. `akebimdru`

`akebimdru`는 QA, 백테스트, 컴플라이언스 문구, 발표 방향 검수 쪽에 가까운 역할을 했다.

우리 프로젝트는 기능 자체보다 표현이 매우 중요했다. 직접적인 매수·매도 지시, 특정 행동 유도, 수익을 확정적으로 말하는 표현은 절대 쓰면 안 됐고, 모든 결과를 "시장 상태 관찰"과 "과거 참고"로 설명해야 했다.

해커톤 금융 주제에서 이 부분은 생각보다 중요하다. 기술적으로 뭔가를 예측하거나 계산할 수 있다고 해서, 그것을 사용자에게 추천처럼 보여줘도 되는 것은 아니다. `akebimdru`는 그 경계선을 팀이 계속 의식하게 만드는 역할을 했다.

## 대회 전

처음부터 우리가 엄청난 준비를 해온 팀은 아니었다.

카톡 로그를 보면 6월 22일부터 24일까지는 주제 자체가 모호했다. "주제 관련 메일 받은 거 있나요", "주제를 모르겠어서요", "어렵네요" 같은 말들이 나온다. 6월 25일 새벽에는 "미리 시작할 수 있다던데"라는 이야기가 나오며 조금씩 움직이기 시작했다.

초기 아이디어는 "패닉셀이나 FOMO 같은 감정투자를 막아주는 것"이었다. 이때만 해도 개인 감정 입력을 받을지, 정보 비대칭을 줄일지, 초보자에게 어떤 정보를 보여줄지 명확하지 않았다.

방향이 선명해진 건 6월 27일 밤이었다.

그날 카톡에서는 깃허브를 파야 한다는 이야기가 나왔고, FOMO Break라는 이름도 이때쯤 나왔다. 처음에는 오타까지 섞인 채로 급하게 오갔지만, 핵심은 이미 있었다. 다른 팀들도 비슷한 주제를 할 수 있으니 차별점이 필요하다는 문제의식이었다.

우리는 FOMO라는 주제 자체가 흔할 수 있다고 예상했다. 그래서 단순 감정 입력 앱이 아니라, 업비트 공개 데이터로 시장 전체의 FOMO 상태를 계산하고, 과거 유사 구간과 자기 점검으로 이어지는 구조를 생각하기 시작했다.

6월 28일 오전 9시 14분경에는 MVP 기능이 거의 확정됐다.

1. FOMO Score
2. Historical Mirror
3. Decision Pause

그리고 10시 20분에는 해야 할 일이 더 구체적으로 정리됐다.

1. FOMO Score 산식을 커스텀한다.
2. 산식에 들어가는 데이터를 크롤링한다.
3. 가져온 데이터로 패턴/시계열 분석을 한다.
4. Score별 거래량, 가격 변동, 기대값 등을 통계적으로 분석한다.
5. 마지막으로 프론트엔드를 만든다.

이 순서는 거의 그대로 하루의 작업 흐름이 됐다.

또 하나 중요한 사전 합의는 제약 조건이었다.

- 투자 추천 문구 절대 금지
- API Key / Secret Key 사용 금지
- 공개 API만 사용
- 계산 결과는 시장 상태 관찰 용도임을 명시

이 원칙 덕분에 프로젝트가 흔들릴 때도 "우리가 만들지 않을 것"이 꽤 분명했다.

## 만든 것

대회 중 실제 작업은 크게 다섯 단계로 나뉘었다.

### 1단계. 공개 데이터 기반을 만든다

가장 먼저 필요했던 건 데이터였다.

FOMO Score도, Mirror도, KNN도 데이터가 없으면 아무것도 할 수 없다. 그래서 업비트 공개 일봉 캔들을 수집하고 검증하는 파이프라인을 만들었다.

중요한 결정은 DB 파일을 공유하거나 커밋하지 않고, `data/upbit_candles_snapshot.csv`와 `data/crawl_report.json`으로 handoff한 점이다. 해커톤에서 DB 파일이 섞이면 충돌도 나고, 누가 어떤 상태의 데이터를 보고 있는지 헷갈리기 쉽다. CSV와 JSON으로 고정한 덕분에 ML, KNN, QA가 같은 기준을 볼 수 있었다.

### 2단계. FOMO Score와 API를 만든다

다음은 FOMO Score였다.

처음에는 CNN Fear & Greed Index를 참고하되, 암호화폐와 초보자 행동에 맞게 지표를 재구성했다. 최종적으로는 가격 모멘텀, 가격 강도, 상승일 거래량 비율, CLV 매수 압력, RSI, 변동성 역수, 거래량 모멘텀, 연속 상승일을 사용했다.

특히 거래량 모멘텀과 연속 상승일에 높은 가중치를 둔 점이 중요했다. 초보자가 "지금 안 타면 놓칠 것 같다"고 느끼는 순간은 보통 거래량이 터지고, 며칠 연속 오르는 장면과 맞닿아 있기 때문이다.

하지만 이 점수를 예측값처럼 표현하지 않기 위해 계속 조심했다. FOMO Score는 가격 예측이 아니라 시장 심리 관찰값이다.

### 3단계. Mirror와 모델 리포트를 붙인다

FOMO Score가 현재를 읽는다면, Mirror는 과거를 되돌아보는 기능이었다.

Historical Mirror는 현재 FOMO Score와 가까운 과거 구간을 찾는다. KNN Mirror는 여기에 1일 변화율, 거래량 비율, RSI 같은 피처를 더해 더 닮은 구간을 찾는다. XGBoost와 expanding-window backtest는 FOMO Score 흐름의 참고 시나리오를 만드는 데 쓰였다.

중간에 문제가 있었다. 모델 결과는 꽤 노이즈가 컸다. XGBoost forecast를 MVP 전면에 보여주기에는 애매했고, KNN 이웃이 너무 최근 날짜에 몰릴 위험도 있었다.

그래서 우리는 방향을 바꿨다.

모델을 "정답을 맞히는 예측기"로 보여주지 않고, "과거 참고와 보조 관찰"로 내려놓았다. 이 결정은 아쉽지만 맞는 결정이었다고 생각한다. 우리가 만들고 싶은 건 투자 추천 서비스가 아니었기 때문이다.

### 4단계. Decision Pause를 제품의 중심에 둔다

FOMO Break의 핵심은 점수가 아니라 멈춤이었다.

사용자가 가상 매수나 가상 매도 버튼을 누르면, 실제 주문 전송 없이 공개 데이터 확인과 Decision Pause로 이어진다. 여기서 사용자는 지금 판단의 근거가 정보인지 감정인지, 과거 참고 사례를 봤는지, 오차 범위를 이해했는지 확인한다.

이 UX는 처음부터 완성되어 있지 않았다. 중간에는 체크가 토글처럼 해제되지 않았고, 체크하면 자동으로 다음 단계로 넘어가 버렸고, 판단 준비도와 실제 Decision Pause의 거리가 멀었다. 발표 직전까지 계속 고쳤다.

하지만 바로 이 부분이 FOMO Break의 차별점이었다.

많은 서비스가 사용자를 더 빠르게 매수/매도 화면으로 보내려고 한다면, 우리는 그 길목에서 일부러 한 번 멈추게 했다.

### 5단계. 발표 가능한 화면으로 압축한다

마지막 단계는 프론트엔드였다.

처음에는 정보가 너무 많았다. 차트, 카드, 설명, 보고서가 한 화면에 다 들어가 있었고, 사용자가 무엇을 해야 하는지 직관적으로 알기 어려웠다. 심지어 글자가 잘리거나 영역을 침범하는 문제도 많았다.

피드백은 분명했다.

> 새로운 사용자가 전혀 적응하지 못한다.

그래서 UI를 갈아엎었다.

기본 화면은 사용자가 한 단계씩 밟는 흐름으로 바꿨다.

1. 가상 매수/매도 시도
2. 공개 데이터 확인
3. Decision Pause
4. 판단 근거 정리

상세 차트와 KNN, 백테스트 리포트는 보고서 파트로 숨겼다. 발표와 시연에서는 "정보량"보다 "사용자가 어떤 경험을 하는지"가 먼저였기 때문이다.

동시에 백테스트와 데이터 품질 검증도 계속됐다. 다만 이 구간에서 모델 결과를 그대로 MVP에 노출하기 어렵다는 판단이 생겼다. 성능이 baseline보다 늘 좋지 않은 구간도 있었고, KNN 결과가 최근 날짜에 몰리는 문제도 있었다.

그래서 "새 모델 개선"보다 "노이즈를 화면과 발표에서 통제하는 전략"이 더 안전하다고 판단했다.

### 15:00-16:30: 프론트엔드가 가장 큰 병목으로 드러나다

오후 3시 34분경 카톡에는 꽤 뼈아픈 평가가 남아 있다.

프론트엔드 폴더가 placeholder에 가깝고, FOMO Score 게이지, Historical Mirror 테이블, Decision Pause 화면이 전부 없어서 발표에서 화면을 보여줄 수 없는 상태라는 내용이었다.

깃허브 기록상 15시 22분 `add mvp frontend dashboard`, 15시 31분 `enhance frontend decision experience`, 16시 00분 `fix frontend api integration`, 16시 13분 `integrate public ticker snapshot`, 16시 28분 `add frontend judgment firewall demo`가 이어졌다.

이때부터 FOMO Break는 API 묶음에서 제품 화면으로 변하기 시작했다.

### 16:30-18:30: 시연 UX와 Decision Pause를 계속 갈아엎다

오후 4시 30분 이후에는 거의 UX 싸움이었다.

UI가 다른 팀과 비슷해 보인다는 걱정이 있었고, 가상 매수/매도 장면이 실제로 보이지 않는다는 피드백도 있었다. 가상 주문 수량 입력, 주문 전송 시도, Decision Pause 전환을 더 명확하게 만들어야 했다.

하지만 한 번에 좋아지지는 않았다.

가로 폭이 부족해서 글씨가 잘리고, 카드가 너무 작아지고, 단계가 한 화면에 들어오지 않고, 정보량이 너무 많아졌다. "보고서 같은 UI"가 되었다가 다시 "사용자 흐름 중심 UI"로 바꾸는 과정을 반복했다.

깃허브 기록에도 이 흔적이 그대로 남아 있다.

- `prevent virtual order panel overflow`
- `connect decision pause transition`
- `tighten decision pause demo layout`
- `prevent compact demo text clipping`
- `shorten compact demo labels`
- `simplify demo microcopy`
- `simplify guided demo UI`
- `rebuild guided self-check UI`

이 커밋명들만 봐도 당시 우리가 무엇과 싸웠는지 보인다. 새로운 기능을 많이 넣는 시간이 아니라, 제품이 깨지지 않고 사용자에게 이해되는 흐름을 만드는 시간이었다.

### 18:30-20:00: 제출물, 발표자료, 시연 영상, 마지막 폴리싱

저녁 6시 30분 이후에는 제출물이 현실로 다가왔다.

필요한 것은 5분 발표용 PDF, 링크 또는 실행 파일로 배포 가능한 결과물, 2분 이내 1GB 이하 시연 영상이었다.

이때 우리는 중간 심사 답변 매뉴얼도 만들었다. 핵심 문장은 이랬다.

> FOMO Break는 투자 추천 앱이 아니라, 사용자가 감정적으로 매수·매도하려는 순간을 가상으로 포착해 실제 주문 경로를 차단하고, Upbit 공개 데이터 기반의 시장 상태·과거 유사 구간·오차 범위를 확인한 뒤 Decision Pause로 자기 점검하게 만드는 판단 방화벽입니다.

이 문장은 제품의 본질을 꽤 잘 요약했다고 생각한다.

7시 45분에는 발표자료 PDF가 공유됐다. 8시 20분대에는 발표 분담과 대본이 오갔다. 우리에게 실제 발표 기회가 올 수도 있다고 생각했고, 시연과 클로징 대본까지 준비했다.

하지만 결과적으로 우리는 무대에 오르지 못했다.

### 20:00 이후: 발표하지 못한 제품

8시가 지나고 나서야 분위기가 이상하다는 걸 알았다. 최종 발표 팀이 이미 따로 불리고 있는 것 같다는 이야기가 나왔다. 8시 34분에는 "비상"이라는 말도 남아 있다.

결국 우리는 발표하지 못했다.

9시 31분에는 "다들 수고했음", "좋은 경험이었음" 같은 말들이 오갔다. 하지만 동시에 "평가 시간이 너무 짧았다", "발표 기회는 줘라"는 아쉬움도 남았다.

개인적으로 가장 아쉬운 건 바로 이 지점이다.

FOMO Break는 설명이 필요한 제품이었다. 단순히 화면만 보면 "코인 점수 앱"처럼 보일 수 있지만, 실제 의도는 그 반대였다. 우리는 매매를 추천하지 않기 위해 표현을 덜어냈고, 사용자의 행동을 빠르게 만들기보다 느리게 만드는 UX를 설계했다.

이 차이는 발표에서 설명해야 전달된다. 그런데 그 기회를 얻지 못했다.

## 남은 것

이번 해커톤은 결과만 보면 실패다. 수상하지 못했고, 발표하지 못했다.

하지만 만든 것만 놓고 보면 실패한 프로젝트라고 생각하지 않는다.

우리는 하루 안에 꽤 많은 것을 만들었다.

- 업비트 공개 데이터 수집 파이프라인
- CSV/JSON 기반 데이터 handoff
- 데이터 검증 리포트
- FOMO Score API
- Historical Mirror
- KNN Mirror
- XGBoost와 expanding-window 기반 참고 리포트
- `/api/mvp-overview` 통합 API
- 실시간 표시용 ticker
- 가상 매수/매도 시도 UX
- Decision Pause
- 판단 근거 정리 화면
- 발표자료와 시연 영상

무엇보다 이 제품은 방향이 있었다.

우리는 가격을 맞히겠다고 하지 않았다. 투자 결정을 대신하겠다고 하지 않았다. 사용자 API Key를 받지 않았고, 개인정보를 받지 않았고, 실거래를 보내지 않았다.

대신 이런 질문을 던졌다.

> 지금 이 판단은 정보에 기반한 것인가, 감정에 끌려가는 것인가?

그 질문을 제품으로 만든 것이 FOMO Break였다.

물론 다음에 다시 한다면 더 잘할 수 있다.

- 발표 가능한 UI를 훨씬 더 빨리 만들 것이다.
- "우리가 하지 않는 것"을 더 강하게 시각화할 것이다.
- 심사 기준에 맞춰 제품의 장점을 더 빨리 포장할 것이다.
- 모델과 리포트보다 사용자 경험을 더 앞에 놓을 것이다.

해커톤에서 좋은 제품을 만드는 것과, 그 제품이 평가 구조 안에서 잘 보이는 것은 다르다. 이번에는 그 차이를 너무 늦게 실감했다.

그래도 나는 FOMO Break가 괜찮은 제품이었다고 생각한다.

아니, 꽤 좋은 제품이었다고 생각한다.

대상을 탔어도 이상하지 않았을 만큼 진지하게 만들었고, 최소한 발표 한 번은 해볼 만한 결과물이었다.

그래서 아쉽다. 하지만 동시에 남는 것도 있다.

우리는 짧은 시간 안에 문제를 정의하고, 데이터를 모으고, 모델을 붙이고, UI를 갈아엎고, 발표 가능한 형태까지 밀어붙였다. 그리고 마지막까지 "투자 추천이 아니라 자기 점검"이라는 원칙을 놓지 않았다.

이번에는 보여주지 못했지만, 다음에는 더 잘 보여줄 것이다.
