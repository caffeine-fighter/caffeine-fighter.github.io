## 글을 쓰며

2026 SKYSH Hackathon이 끝났다.

끝나고 나서 깃허브 커밋이랑 카카오톡 회의 로그를 다시 열어 봤다. 기억만으로 쓰면 내가 한 일을 부풀릴 수도 있고, 그날 무슨 판단을 거쳐 제품이 바뀌었는지 빼먹을 수도 있을 것 같았다. 기록에는 오전에 처음 방향을 잡을 때부터 마지막 제출과 발표 준비까지 거의 분 단위로 남아 있었다.

그래서 그 하루를 처음부터 순서대로 다시 따라가 보려고 한다. 그때 뭘 알고 있었고 뭘 골랐는지, 그게 다음 작업에 어떻게 이어졌는지. 결과 얘기는 실제로 결과가 나온 시점에서 하겠다.

## 참가 동기와 팀 결성

개인적으로는 짧은 시간 안에 제품 방향을 정하고 MVP를 직접 끝까지 끌고 가 보고 싶었다. 대회나 MVP 개발 해커톤에 나가 본 적은 여러 번 있었지만, 제품 방향과 구현을 메인에 가까운 자리에서 책임진 건 거의 처음이었다. 남이 잡은 방향을 구현하는 데서 끝나지 않고, 어떤 문제를 풀지부터 시연 가능한 화면까지 내가 이어 붙일 수 있는지 확인해 보고 싶었다.

팀은 꽤 급하게 꾸렸다. 참가 마감 당일에 공과대학 만화·애니·게임 동아리 애니뮤의 프로그래밍 소모임에서 팀원을 구했는데, 갑작스러운 제안이었는데도 `cyanbackpack`, `knowin-kyeong`, `Akebimdru`가 같이 해 줬다. 팀 이름은 마감 직전에 떠오르는 단어를 그냥 넣었다가 **근고르기**라는 괴상한 이름이 됐다.

네 명의 경험은 꽤 달랐다. `knowin-kyeong`은 대회 경험이 가장 많았고 AI가 주 분야였지만 MVP 개발은 처음이었다. 나는 대회와 MVP 개발 해커톤은 여러 번 나갔지만 제품을 직접 총괄해 본 건 거의 처음이었다. `cyanbackpack`과 `Akebimdru`는 컴퓨터공학 지식은 있었지만 개발 프로젝트도 해커톤도 처음이었다.

그래서 한 사람이 다 끌고 가기보다는, 제한 시간 안에 터질 수 있는 일들을 나눠 맡는 식으로 역할을 정했다.

1. `cyanbackpack`: 공개 데이터 수집·검증·재현성
2. `caffeine-fighter`: MVP 총괄·백엔드 API 연결·시연 UX
3. `knowin-kyeong`: ML·KNN·XGBoost·모델 리포트
4. `Akebimdru`: QA·백테스트·컴플라이언스 문구·발표 방향 검수

돌아보면 역할 배정 자체는 대체로 맞았다.

`cyanbackpack`이 맡은 데이터 파이프라인은 할 일이 비교적 분명했다. 어떤 API에서 뭘 가져오고, 어떤 형식으로 공유하고, 뭘 검증할지 정하면 결과물이 나왔다. 그렇다고 덜 중요한 일은 아니었다. 여기가 무너지면 점수와 모델이 서로 다른 데이터를 보게 된다. 검증된 CSV와 JSON이 일찍 나와서 나머지 셋이 같은 기준으로 움직일 수 있었다.

내 쪽은 맥락 전환이 제일 많았다. 프로젝트 구조와 브랜치 규칙을 정하다가 백엔드 응답을 맞추고, 다시 프론트엔드로 넘어가 시연 흐름을 고쳤다. 마지막에는 발표자료와 영상도 같은 제품을 설명하도록 맞춰야 했다. 메인에 가까운 자리는 처음이라 내가 병목이 된 순간도 있었다.

`knowin-kyeong`은 대회 경험과 AI 역량이 있어서, 우리가 직접 만들 FOMO 지표와 과거 패턴, 시계열 모델을 맡기기에 제일 자연스러웠다.

`Akebimdru`의 역할은 개발 속도로만 보면 눈에 덜 띌 수 있다. 그런데 금융 주제는 표현 하나로 제품 성격이 바뀐다. “오를 가능성이 있다”와 “과거에 이런 구간이 있었다”는 완전히 다른 말이다. 직접적인 행동 유도나 수익 보장 표현을 걷어내고, 백테스트와 발표 문구가 투자 추천처럼 읽히지 않는지 봐 줄 사람이 필요했다.

## 준비 과정

처음부터 준비가 잘된 팀은 아니었다.

6월 22일부터 24일까지 카카오톡에는 “주제 관련 메일 받은 거 있나요”, “주제를 모르겠어서요”, “어렵네요” 같은 말이 남아 있다. 25일 새벽에야 미리 시작해도 된다는 얘기가 나왔고, 초기 아이디어도 패닉셀이나 FOMO 같은 감정 투자를 막자는 정도였다. 개인 감정을 직접 입력받을지, 초보자에게 뭘 보여줄지, 정보 비대칭은 어떻게 줄일지도 정해진 게 없었다.

방향은 6월 27일 밤에 잡혔다. 다른 팀도 비슷한 주제를 고를 수 있으니 차별점이 있어야 했다. 개인 감정 데이터를 받는 대신 업비트 공개 데이터로 시장 전체가 얼마나 과열됐는지 보고, 사용자가 행동하기 전에 한 번 멈추게 하자는 쪽으로 정했다. **FOMO Break**라는 이름도 이때 나왔다.

대회 당일 오전 9시 14분쯤 MVP를 세 기능으로 좁혔다.

1. FOMO Score
2. Historical Mirror
3. Decision Pause

10시 20분에는 점수 산식, 데이터 크롤링, 패턴·시계열 분석, 통계 분석, 프론트엔드 순으로 작업하기로 했는데, 이 순서가 거의 그대로 그날 하루의 작업 순서가 됐다.

### 최종적으로 만들고자 한 FOMO Break

세부 기능이 언제 붙고 어떻게 바뀌었는지는 뒤에서 시간순으로 쓰고, 여기서는 하루 동안 완성하려던 제품의 전체 모습만 먼저 적어 둔다.

FOMO Break는 업비트 공개 데이터로 시장의 공포·탐욕 상태를 보고, 초보 사용자가 감정적으로 매수·매도하려는 순간 한 번 멈추게 하는 MVP다.

흔한 코인 예측기나 매수·매도 신호를 만들고 싶지는 않았다. 오히려 반대로, 결정을 늦추고 한 번 더 생각하게 만드는 서비스를 만들고 싶었다.

사용자가 거치는 순서는 공개 데이터 확인, FOMO Score, 과거 유사 구간, Decision Pause였고, 제일 중요한 건 마지막 단계였다.

1. 업비트 공개 캔들 데이터를 수집하고 오류를 검증한다.
2. 8개 지표로 FOMO Score를 계산한다.
3. Historical Mirror와 KNN Mirror로 닮은 과거 구간을 보여준다.
4. 가상 매수·매도 시도는 실제 주문으로 보내지 않고 Decision Pause로 넘긴다.
5. 사용자가 자기 판단의 근거가 정보인지 감정인지 직접 확인한다.

지킬 선도 미리 정했다.

- 사용자 API Key나 Secret Key를 받지 않는다.
- 개인정보를 수집하지 않는다.
- 투자 추천·자문·수익 보장 문구를 쓰지 않는다.
- 계산 결과는 시장 상태 관찰과 과거 참고 사례로만 설명한다.

FOMO Score에는 가격 모멘텀, 가격 강도, 상승일 거래량 비율, CLV 매수 압력, RSI, 변동성 역수, 거래량 모멘텀, 연속 상승일을 썼다. 그중 거래량 모멘텀과 연속 상승일에 가중치를 높게 줬다. 초보자가 “지금 안 타면 놓칠 것 같다”고 느끼는 때가 대개 거래량이 확 늘고 며칠 연속 오르는 구간이라고 봤기 때문이다.

산식은 CNN Fear & Greed Index를 출발점으로 참고했지만, 암호화폐 공개 데이터와 초보 사용자 행동에 맞게 다시 짰다. 기존 지표 이름만 빌려 온 건 아니고, 우리가 실제로 수집할 수 있고 제품에서 설명할 수 있는 값들로 좁혔다.

그리고 이 점수가 예측처럼 보이지 않게 하는 데 꽤 신경을 썼다. FOMO Score는 어디까지나 시장 심리를 관찰한 값이었다.

Historical Mirror도 같은 이유로 만들었다. 현재와 점수가 비슷했던 과거 구간을 보여주지만, 그 뒤 수익률을 미래 예측처럼 말하지는 않았다. KNN Mirror는 점수 하나만 비교하지 않고 1일 변화율, 거래량 비율, RSI까지 같이 봤다. 지금 시장이 과거 어느 때와 닮았는지 참고하게 할 뿐이고, 그때와 같은 결과가 나온다고 약속하지는 않았다.

프론트엔드에서는 이 기능들을 **Judgment Firewall**이라는 흐름으로 묶기로 했다. 사용자가 가상 매수나 매도를 눌러도 주문은 나가지 않는다. 대신 표시용 현재가와 시장 상태, 과거 구간과 오차 범위를 보고, 체크리스트로 자기 판단의 근거를 확인하게 했다. 이름은 거창하지만 하고 싶은 건 단순했다. 흥분한 상태에서 버튼부터 누르는 걸 몇 분이라도 늦추는 것.

이제 이걸 하루 안에 실제 화면으로 만들어야 했다.

## 대회 중 경과

### 09:00–12:00 — 데이터와 백엔드부터 잠그다

오전에는 행사장 도착, 깃허브 권한 설정, API 조사, MVP 기능 정리가 한꺼번에 굴러갔다. 10시 30분쯤 역할을 나누고 나서부터는 각자 병렬로 움직였다.

깃허브 기록을 보면 11시 9분에 프로젝트 구조 초기화 커밋, 11시 21분에 README 정리, 11시 38분에 Historical Mirror API, 11시 46분에 관련 테스트가 올라갔다.

나는 프로젝트 구조와 기준 브랜치를 잡고 Historical Mirror와 `/api/mvp-overview`를 붙였다. 그 뒤로 KNN Mirror와 비교할 수 있게 응답 계약을 맞추고, API 파라미터 검증과 문서를 정리했다.

`cyanbackpack`은 업비트 공개 캔들 수집과 검증을 맡았다. 실제로 공유한 데이터는 KRW-BTC, KRW-ETH, KRW-XRP 각각 565행, 총 1,695행이었고 missing dates, duplicate dates, OHLC errors, value errors는 모두 0이었다. 11시 40분쯤에는 업비트 클라이언트 확장과 테스트 20개 통과 소식도 올라왔다.

해커톤에서 데이터가 있다는 것과 모두가 같은 검증된 데이터로 다시 돌려볼 수 있다는 건 꽤 다른 문제다. DB 파일은 커밋하지 않고 `data/upbit_candles_snapshot.csv`와 `data/crawl_report.json`으로 넘기기로 했다. DB 파일을 그대로 공유하면 충돌도 나고 누가 어느 시점 데이터를 보는지 헷갈린다. CSV와 JSON으로 고정해 둔 덕에 뒤에서 점수, Mirror, ML 리포트가 다 같은 데이터로 돌아갔다.

오전 안에 눈에 보이는 화면이 나온 건 아니었지만, 데이터를 가져와 검증하고 점수를 계산해서 과거 구간을 찾는 백엔드 뼈대는 세웠다.

### 12:00–15:00 — Mirror와 모델을 제품 안에 넣다

정오 이후에는 협업 규칙부터 정했다. 공용 기준 브랜치는 `feature/historical-mirror-polish`였고, 각자 작업 브랜치에서 PR을 올리기로 했다. force push와 공용 브랜치 직접 커밋은 금지했다.

12시 35분에서 50분 사이에 크롤링 PR과 데이터 export가 정리됐다. 오후 1시 25분쯤에는 Historical Mirror와 KNN Mirror를 같은 화면에서 비교할 수 있도록 응답 구조를 맞췄고, `/api/mvp-overview`는 KNN을 기본으로 돌리지 않고 `include_knn=true`일 때만 포함하게 했다.

1시 22분 이후로는 ML 작업도 빠르게 불어났다. 깃허브에 `feat: add KNN mirror and FOMO score forecast`, `KNN k-optimization`, `XGBoost FOMO Score training`, `expanding-window backtest`, `feat(viz): final 7 graphs — ensemble redrawn as stitched timeline` 같은 커밋이 남아 있다.

`Akebimdru` 쪽에서는 11시 52분 `feat: add FOMO score backtest and quality report`, 13시 27분 `feat: expand FOMO score sensitivity backtest`가 이어졌다. 모델 붙이는 일과는 따로, 점수 산식의 민감도와 품질, 그리고 어디까지가 안전한 표현인지 확인하는 작업이었다.

Historical Mirror는 현재 FOMO Score와 가까운 과거 구간을 찾고, KNN Mirror는 1일 변화율·거래량 비율·RSI 같은 피처까지 비교했다. XGBoost와 expanding-window backtest도 FOMO Score의 참고 흐름을 보여주려고 붙였다.

그런데 개발하면서 보니 예측 결과가 시점과 모델에 따라 크게 흔들렸다. 초기 실험 일부에서는 baseline보다 못한 구간도 있었고, KNN 이웃이 너무 최근 날짜로 몰릴 위험도 있었다. 최종 저장소에서는 XGBoost가 세 마켓 모두 persistence baseline보다 나은 구간을 확보했지만, 대회 중에는 그걸 일반적인 가격 예측 성능이라고 말할 근거가 부족했다.

여기서 골라야 했다. “AI가 미래를 예측한다”고 포장하면 발표는 더 화려해 보였을 거다. 대신 성능이 애매한 숫자를 강한 예측처럼 말하게 된다.

우리는 그렇게 하지 않았다.

모델은 정답을 맞히는 예측기 대신 과거 참고용, 보조 관찰 리포트로 내렸다. 숫자를 세게 말하는 것보다 처음 정한 선을 지키는 쪽이 맞다고 봤다. 아쉬움이 없진 않았지만 지금 다시 해도 같은 선택을 할 것 같다.

### 15:00–18:30 — 프론트엔드가 가장 큰 병목이 되다

오후 3시 34분쯤, 프론트엔드가 사실상 placeholder 수준이고 발표에서 보여줄 화면이 없다는 평가가 나왔다. FOMO Score 게이지도, Historical Mirror 테이블도, Decision Pause 화면도 제대로 안 보였다.

그때부터는 거의 프론트엔드에만 붙어 있었다.

깃허브에는 15시 22분 `add mvp frontend dashboard`, 15시 31분 `enhance frontend decision experience`, 16시 `fix frontend api integration`, 16시 13분 `integrate public ticker snapshot`, 16시 28분 `add frontend judgment firewall demo`가 연달아 남아 있다. 이 무렵부터 FOMO Break가 API 묶음에서 실제 제품 화면 비슷한 모양이 되기 시작했다.

한 번에 좋아지지는 않았다. 가로 폭이 모자라 글자가 잘렸고, 체크를 해제할 수 없었고, 체크하면 다음 단계로 멋대로 넘어갔다. 판단 준비도와 실제 Decision Pause 사이도 너무 멀었다. 차트, 카드, 설명을 다 넣다 보니 사용자가 뭘 해야 하는지가 안 보였다.

> 새로운 사용자가 전혀 적응하지 못한다.

맞는 말이었다. 처음에는 차트, 카드, 설명, 리포트를 한 화면에 다 보여주려 했는데, 정보가 많으면 기술적으로 완성도가 높아 보일 거라고 착각했던 것 같다. 그래서 상세 차트와 KNN, 백테스트는 보고서 쪽으로 내리고, 기본 화면에는 가상 매수·매도 시도, 공개 데이터 확인, Decision Pause, 판단 근거 정리만 남겼다.

다른 서비스들이 사용자를 매수·매도 화면으로 빨리 보내려 한다면, 우리는 그 길목에서 일부러 한 번 멈추게 하고 싶었다. 그러니 점수나 모델보다 이 흐름이 먼저 눈에 들어와야 했다.

커밋명에 그때 씨름한 흔적이 그대로 남아 있다.

- `prevent virtual order panel overflow`
- `connect decision pause transition`
- `tighten decision pause demo layout`
- `prevent compact demo text clipping`
- `shorten compact demo labels`
- `simplify demo microcopy`
- `simplify guided demo UI`
- `rebuild guided self-check UI`

거창한 새 기능은 거의 없다. 화면이 넘치지 않게 하고, 잘리는 글자를 줄이고, 버튼을 누른 다음 단계가 제대로 이어지게 하는 수정들이다. 오후 4시 30분부터 6시 30분까지는 제품을 키웠다기보다, 겨우 제품처럼 보이고 실제로 시연이 되게 만드는 데 다 썼다.

지금 저장소에서 내 author 표기 두 개를 합치면 merge commit 포함 90개가 넘는 커밋이 있다. 프론트엔드 대부분과 시연 영상, 백엔드 상당 부분, 발표 직전 폴리싱을 내가 했다. 숫자 자랑을 하려는 건 아니고, 이 프로젝트를 대충 굴리지는 않았다는 건 남겨 두고 싶다.

문제는 데이터, 모델, 검수 결과가 쌓이는 동안 발표 화면 만드는 일이 후반에 내 쪽으로 너무 몰렸다는 거다. 역할 배정은 맞았지만, 각자 만든 결과가 화면에서 어떻게 보이는지 같이 확인하는 구조가 없었다.

### 18:30 이후 — 제출과 발표 준비

저녁 6시 30분이 넘어가자 제출이 코앞으로 다가왔다. 5분 발표용 PDF, 링크나 실행 파일로 배포할 수 있는 결과물, 2분 이내·1GB 이하 시연 영상을 내야 했다.

중간 심사 답변도 한 문장으로 다듬었다.

> FOMO Break는 투자 추천 앱이 아니라, 사용자가 감정적으로 매수·매도하려는 순간을 가상으로 포착해 실제 주문 경로를 차단하고, Upbit 공개 데이터 기반의 시장 상태·과거 유사 구간·오차 범위를 확인한 뒤 Decision Pause로 자기 점검하게 만드는 판단 방화벽입니다.

7시 45분에 발표자료 PDF가 공유됐고, 8시 20분대에는 발표 분담과 대본이 오갔다. 발표 기회가 올 거라고 생각해서 시연과 마지막 문장까지 준비했다. 끝까지 버티려고 몬스터도 마셨다.

화면만 보면 코인 점수 앱으로 오해하기 쉬워서 발표가 특히 중요했다. 왜 실제 주문을 막았는지, 왜 모델을 참고 자료 정도로 낮췄는지, Decision Pause가 기존 서비스와 뭐가 다른지를 말로 이어 줘야 했다. 그 설명까지 준비는 끝내 둔 상태였다.

8시가 넘어가면서 분위기가 이상해졌다. 최종 발표 팀이 이미 따로 불리고 있는 것 같다는 얘기가 돌았고, 8시 34분 카카오톡에는 “비상”이라는 말이 남아 있다. 그때까지는 정확한 결과를 몰랐다.

## 결과

우리 팀은 최종 발표 대상에 들지 못했다. 수상도 못 했다.

9시 31분쯤 “다들 수고했음”, “좋은 경험이었음” 같은 말을 주고받고 끝났다. 발표할 줄 알고 카페인을 때려 넣은 탓에 잠도 안 왔고, 다음 날 강의와 바로 이어진 다른 대회 일정까지 그대로 꼬였다. 결과가 나오기 전까지 대본이랑 기능을 붙잡고 있던 대가를 몸으로 치르고 나니 더 허탈했다.

개인적으로 제일 아쉬운 건 발표 기회를 못 얻은 거였다. FOMO Break는 설명이 필요한 제품이었다. 화면만 보면 코인 점수 앱 같지만 실제 의도는 그 반대였다. 매매를 추천하지 않으려고 표현을 덜어냈고, 사용자가 더 빨리 움직이기보다 더 느리게 움직이도록 UX를 짰다. 그 차이는 발표에서 말로 해야 전달되는데, 우리는 그 자리를 얻지 못했다.

### 내가 결과를 납득하지 못한 이유

여기서부터는 좀 공격적으로 들려도 어쩔 수 없다. 나는 아직도 이 결과를 완전히 납득하지 못한다.

대회 진행이나 공간, 분위기에는 큰 불만이 없었다. 문제라고 생각한 건 심사였다. 행사를 잘 만들었어도 마지막 평가가 전문성과 설명 책임을 보여주지 못하면, 참가자 기억에 오래 남는 건 그 부분이다.

내가 보기에는 5개 학교에서 한 명씩 심사위원을 맡은 구조였던 것 같다. 정확한 내부 사정은 모른다. 그나마 제대로 대화가 된다고 느낀 건 서울대 측 심사위원이었다. 그날 밤 순위를 물어봤더니 우리 팀이 딱 중간쯤이었다고 했다. 뭐가 결정적인 문제였는지 물어도 선명한 답은 없었다. 내가 확인한 약점은 프론트엔드 완성도와 팀 이름 정도였고, 들은 설명은 주제가 겹쳤고 평가 기준이 서로 달랐다는 쪽에 가까웠다.

그 말은 위로가 안 됐다. 같은 주제라도 어떤 관점으로 풀었고 어디까지 구현했는지를 보는 게 해커톤이라고 생각한다. 우리는 코인 점수만 띄워 놓지 않았다. 매수·매도 신호를 피했고, 공개 데이터만 썼고, 과거 유사 구간과 Decision Pause를 한 흐름으로 묶었다.

그 차이가 안 보였다면 심사가 제대로 돌아갔다고 보기 어렵다. 운영은 해커톤이었는데 심사는 아이디어 발표회와 인기투표 사이 어디쯤에 걸쳐 있었던 느낌이다.

이 정도면 꽤 돌려 말한 거다.

집에 가는 길에 친구한테 “내가 버스 탄 해커톤은 다 잘되고, 내가 버스 운전한 해커톤은 다 망한다”고 보냈다. “나는 아직 능력이 부족한가봄”이라고도 했다. 근데 이건 너무 공격적으로 보이지 않으려고 한 말에 가까웠다.

속내는 달랐다. 나는 내 능력을 의심하지 않았다. 프론트엔드와 영상, 백엔드 상당 부분을 붙잡고 내 이름으로 커밋을 90개 넘게 남긴 프로젝트를, 발표 한 번 없이 중간쯤으로 처리한 심사 구조를 의심했다.

같은 팀 ML 담당이었던 `knowin-kyeong`은 [자신의 후기](https://knowin-kyeong.github.io/%EB%8C%80%ED%9A%8C%20%ED%9B%84%EA%B8%B0/fomo-break-hackathon-review/)에서 이 결과를 다르게 복기했다. 사전 준비가 부족했고, 정량 모델에 집중하느라 해커톤이 평가하는 문제 정의와 스토리텔링을 놓쳤으며, 다른 발표팀 결과물을 보고 나서는 탈락을 납득했다고 썼다.

그 분석이 틀렸다고는 생각하지 않는다. 그는 ML 파트에서 모델의 한계와 다른 팀 발표를 중심으로 대회를 봤고, 나는 제품 전체 구현량과 심사위원에게 직접 들은 얘기를 중심으로 결과를 봤다. 같은 팀이어도 맡은 영역과 결과를 접한 방식에 따라 판단이 갈릴 수 있다. 그의 오답노트와 내 문제의식은 같이 읽으면 좋겠다.

물론 내 잘못도 있었다. 발표 가능한 UI를 더 일찍 만들었어야 했고, 팀 이름도 덜 이상하게 지었어야 했다. 제품의 차별점도 심사자가 놓칠 수 없게 더 노골적으로 보여줬어야 했다. 그래도 우리가 발표조차 못 할 수준이었다는 판단에는 동의하지 않는다. 백엔드, 데이터 파이프라인, 모델 리포트, Decision Pause 설계를 놓고 보면 적어도 기술적 깊이로 밀릴 프로젝트는 아니었다고 생각한다.

대상을 탔어도 이상하지 않을 만큼 진지하게 만들었고, 최소한 발표 한 번은 해 볼 만한 결과물이었다. 객관적인 순위를 단정하려는 건 아니고, 구현과 기록을 다시 훑어본 지금의 내 생각이다.

## 오답노트

결과를 납득 못 한다고 내가 고칠 게 없다는 뜻은 아니다. 내가 바꿀 수 있었던 것과 직접 바꾸기 어려웠던 걸 나눠 봤다.

### 내가 바꿀 수 있었던 것

- 첫 세 시간 안에 빈 데이터로라도 발표 가능한 최소 화면을 만들었어야 했다.
- 데이터·모델·QA 담당도 중간부터 시연 화면을 함께 검수하게 했어야 했다.
- “우리가 하지 않는 것”과 Decision Pause의 차별점을 첫 화면에서 더 강하게 보여줬어야 했다.
- 모델과 리포트를 늘리기 전에 사용자가 밟을 한 가지 흐름부터 잠갔어야 했다.
- 심사 기준에 맞는 한 문장과 시연 순서를 더 일찍 확정했어야 했다.
- 팀 이름처럼 제품 외부에서 감점될 수 있는 요소도 가볍게 보지 말았어야 했다.

제일 큰 실수는 프론트엔드를 작업 순서 맨 끝에 둔 거다. 데이터와 산식이 있어야 화면을 만들 수 있다는 논리 자체는 맞았다. 그런데 해커톤에서는 데이터가 덜 됐어도 사용자가 뭘 누르고 뭘 보게 되는지부터 보여줘야 한다. 우리는 제품의 머리부터 만들고 얼굴은 너무 늦게 들여다봤다. 좋은 걸 만드는 것과 평가하는 사람이 그 장점을 바로 알아보게 만드는 건 또 다른 일인데, 이번에는 그걸 너무 늦게 챙겼다.

다음에는 첫 화면부터 만든다.

### 내가 직접 바꾸기 어려웠던 것

- 최종 발표팀을 고르는 심사위원의 전문 분야와 평가 기준
- 짧은 평가 시간 안에 각 저장소와 구현을 얼마나 깊게 확인했는지
- 비슷한 주제를 선택한 팀이 여러 개였다는 사실
- 발표 기회를 받지 못하면 제품의 의도를 설명할 방법이 거의 없었던 구조

이건 내가 더 열심히 구현한다고 바뀌는 부분이 아니다. 대신 다음 대회를 고를 때 심사위원의 전문성과 평가 방식, 중간 피드백과 최종 발표 기회가 어떻게 주어지는지를 먼저 확인할 수는 있다.

참가자의 시간과 노동을 가져가는 대회라면 결과를 납득시킬 평가와 피드백까지 책임져야 한다고 생각한다. 운영이 괜찮았던 것도, 심사가 아쉬웠던 것도 둘 다 사실인데, 내 기억에 더 오래 남은 건 심사 쪽이다.

## 그래도 잘한 것

하루 동안 실제로 만든 건 이만큼이다.

- 업비트 공개 데이터 수집·검증 파이프라인
- CSV·JSON 기반 데이터 공유
- 데이터 검증 리포트
- FOMO Score API
- Historical Mirror와 KNN Mirror
- XGBoost·expanding-window 참고 리포트
- `/api/mvp-overview` 통합 API와 실시간 표시용 ticker
- 가상 매수·매도 시도와 Decision Pause
- 판단 근거 정리 화면
- 발표자료와 시연 영상

당일 처음 공유한 데이터는 1,695행이었는데, 이후 저장소에서 장기 백테스트용 데이터를 세 마켓 각각 2,200일, 총 6,600행까지 늘렸다. 최종 기록에는 전체 테스트가 `120 passed, 5 skipped`로 남아 있다. 행사장에서 한 번 돌아간 데모로 끝내지 않고, 대회가 끝난 뒤에도 다시 돌리고 검증할 수 있는 형태로 정리해 뒀다.

네 명이 나눈 역할도 실제 결과물로 이어졌다. 검증된 데이터가 있었고, 모델의 한계를 확인한 다음 제품 안에서 위치를 조정했고, 투자 추천처럼 보이지 않게 문구를 관리했다. 급하게 모인 팀이 하루 만에 여기까지 온 건 각자 맡은 걸 끝까지 놓지 않아서였다. 혼자였다면 백엔드와 화면은 만들었을지 몰라도, 검증 데이터와 모델 리포트, 규정 문구까지 다 갖추지는 못했을 거다.

그중 내가 제일 좋게 보는 건 끝까지 투자 추천 쪽으로 방향을 틀지 않았다는 점이다. 사용자 API Key와 개인정보를 받지 않았고, 실거래를 보내지 않았고, 가격을 맞힌다고 말하지 않았다. 대신 지금 이 판단이 정보에 기반한 건지, 감정에 끌려가는 건지를 물었다.

나는 FOMO Break가 괜찮은 제품이었다고 생각한다.

아니, 꽤 좋은 제품이었다고 생각한다.

처음으로 제품 방향과 구현을 중심에서 끌고 가서, 마지막까지 실제로 시연할 수 있는 형태로 완주했다는 것도 남았다. 결과와는 별개로, 이번 이후로는 백엔드, 프론트엔드, 발표를 따로 보지 않고 하나의 사용자 흐름으로 묶어서 챙겨야 한다는 기준이 생겼다.

## 앞으로
