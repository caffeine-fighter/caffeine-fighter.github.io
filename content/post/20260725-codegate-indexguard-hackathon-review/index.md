## 글을 쓰며

7월 21일부터 23일까지 **CODEGATE 2026 AI 스타트업 해커톤**에 참가했다. 세 명이 한 팀이 되어 문서가 RAG의 지식으로 들어가기 전에 변조와 공격을 찾아내는 제품을 만들었다.

이 글에서는 결과부터 요약하지 않는다. 왜 이 문제를 골랐는지, 세 서비스를 어떻게 나눴는지, 3일 동안 어떤 순서로 제품과 발표를 완성했는지를 먼저 적는다. 마지막에는 작동하는 제품을 만드는 일과 처음 보는 사람에게 그 가치를 이해시키는 일이 어디에서 갈렸는지 정리한다.

이번에 만든 프로젝트는 **IndexGuard**다.

> 기억 전에, 검증.

## IndexGuard

IndexGuard는 PDF, DOCX, HWPX 문서의 변경을 규칙과 AI로 분석해 숫자·정책 왜곡과 간접 프롬프트 인젝션이 RAG 지식으로 저장되기 전에 차단하는 문서 무결성 게이트다.

RAG는 보통 답변 단계의 환각이나 프롬프트 공격을 많이 걱정한다. 그런데 문서가 처음부터 오염된 상태로 색인되면 답변 모델은 그 문서를 정상적인 회사 지식으로 받아들인다. 사후 필터만으로는 이미 틀린 지식을 기억한 상태가 된다.

우리는 답변이 아니라 **색인 직전**을 막기로 했다.

예시는 단순하다.

| 원문과 변경문 | 판정 |
|---|---|
| `김지훈 월급 2,000,000원` → `김지훈의 월급 2,000,000원` | 의미가 같으므로 통과 |
| `2,000,000원` → `20,000,000원` | 금액 변조로 차단 |
| `월급` → `일급` | 지급 주기 변경으로 차단 |
| `김지훈` → `김철수` | 적용 대상 변경으로 차단 |

모든 글자 차이를 위험하다고 하면 그냥 시끄러운 diff 도구가 된다. 반대로 문장의 대충 비슷한 의미만 보면 숫자, 단위, 사람 이름처럼 작은데 치명적인 변경을 놓친다.

그래서 IndexGuard는 결정적 diff와 정적 규칙으로 핵심 변경을 먼저 잡고, 독립된 AI 분석 서비스가 정책 의미와 프롬프트 인젝션 가능성을 해석하게 했다. 최종 결과는 `ALLOW / REVIEW / BLOCK`, 실제 색인 동작은 `INDEX / HOLD / QUARANTINE`으로 분리했다.

`BLOCK`을 빨간색으로 보여주는 데서 끝내지 않은 것도 중요했다. 공격 문서는 실제 색인기에 들어가지 않고, 이전에 승인된 안전한 버전이 그대로 남는다. 우리 데모의 핵심은 분석 화면이 아니라 이 장면이었다.

## 왜 HWPX였나

한컴이 후원사였기 때문에 HWPX 지원은 처음부터 P0로 잡았다.

그냥 후원사 이름을 발표 자료에 넣는 것보다, 한컴이 실제로 많이 만나는 공공·기업 문서 환경을 제품의 중심에 두는 게 낫다고 봤다. PDF만 지원하는 문서 AI 보안 도구는 많아질 수 있지만, HWPX를 안전하게 파싱하고 변경 근거까지 보여주는 제품은 한국 시장에서 설명할 이유가 분명하다.

HWPX는 ZIP과 XML 기반이라 본문 추출만 하면 끝나는 형식도 아니다. 비정상 압축, 외부 관계, 스크립트 payload, OLE, 숨김 스타일 같은 입력 자체가 분석기를 공격할 수 있다. 그래서 파일 형식 검증과 용량 제한을 먼저 적용하고, 문제가 있으면 자동 통과가 아니라 실패 상태로 남기는 fail-closed 원칙을 썼다.

레거시 바이너리 HWP까지 욕심내지는 않았다. HWPX를 대표 입력으로 완성하고 PDF와 DOCX를 같은 파이프라인에 연결하는 쪽이 24시간 안에는 맞았다.

## 세 명의 역할

팀은 A, B, C 세 서비스로 나눴다.

### 문서 수집·무결성·색인 게이트웨이

내 역할이었다.

- 감시 폴더의 문서 생성·수정 감지
- PDF, DOCX, HWPX 안전한 정규화
- 이전 버전과 변경 버전의 diff 생성
- 원본·정규화 본문 SHA-256과 버전 기록
- B 서비스로 분석 요청 전달
- 승인 문서만 RAG에 색인
- 위험 문서 HOLD·격리·재분석 상태 관리

추가로 Git working tree의 staged·unstaged diff를 직접 감시하는 기능과, AI 호스트가 B 분석을 실행할 수 있는 MCP 서버도 만들었다.

내가 절대 하지 않는 일도 정했다. A는 AI 위험도를 직접 계산하지 않고 대시보드를 구현하지 않는다. 파일과 색인 권한을 가진 서비스가 자기 판단까지 해버리면 역할 분리가 무너진다.

### AI 위험 분석·감사 엔진

B는 A가 넘긴 정규화 전후 텍스트와 변경 구간만 본다. 원본 파일 저장소와 RAG 색인기에는 접근하지 않는다.

결정적 규칙을 항상 먼저 실행하고, 로컬 LLM은 변경 요약과 정책 의미, 간접 프롬프트 인젝션 가능성을 분석한다. 고위험 변경은 한 번 더 감사한다. LLM이 실패하거나 이상한 JSON을 내놓아도 자동 승인이 되지 않게 했다.

### 운영 대시보드·승인 콘솔

C는 문서 목록, 버전 이력, diff, 위험 근거와 색인 상태를 보여준다. 운영자는 여기서 승인, 보류, 재분석을 요청한다.

C도 위험 점수를 직접 계산하거나 색인 DB를 조작하지 않는다. A와 B가 제공한 상태와 근거를 사람이 이해할 수 있게 보여주는 역할이다.

이 구분 덕분에 세 명이 병렬로 작업할 수 있었다. 공통 JSON 계약을 먼저 고정하고, 각자 자기 서비스만 구현했다. 충돌이 없으면 바로 push와 merge를 했고, 3시간마다 실제 연결 상태를 확인했다.

해커톤에서는 예쁜 역할표보다 경계가 중요하다. 누가 어떤 코드를 짜는지도 중요하지만, **누가 절대 어떤 권한을 가지면 안 되는지**까지 정해야 병렬 작업이 된다.

## 대회 중 경과

### 7월 21일 — 일단 돌아가게 만든다

대회 첫날 오전에는 제품 문장, 데모 시나리오, JSON 계약과 역할을 먼저 동결했다.

오전 11시 30분에 MVP 전략 문서가 올라갔고, 12시 33분에는 첫 문서 무결성 게이트웨이가 들어갔다. 오후 3시 22분에는 A 게이트웨이와 Git diff watcher가 붙었다. 저녁에는 대시보드, B 위험 엔진, 제품 데모 파이프라인이 차례로 `main`에 합쳐졌다.

속도는 꽤 빨랐다.

그 대신 계속 생기는 문제가 있었다.

- A와 B가 같은 `decision`을 서로 다른 의미로 쓰는 문제
- `ALLOW`와 실제 `INDEX`를 같은 사건처럼 취급하는 문제
- 재분석 결과가 이전 후보 SHA와 섞일 수 있는 문제
- 대시보드가 브라우저에서 권위 있는 상태를 다시 계산하는 문제
- B가 죽었을 때 문서가 애매하게 통과할 수 있는 문제

이런 건 화면만 보면 잘 안 보인다. 계약과 상태 머신을 실제로 연결할 때 드러난다.

우리는 `ALLOW + INDEX` 결과가 나와도 C의 승인이 없으면 `HOLD`를 유지하고, 승인 시점의 후보 SHA-256이 현재 후보와 같을 때만 색인하도록 바꿨다. B가 죽거나 계약에 맞지 않는 응답을 보내면 문서는 실패 상태에 남고 색인되지 않는다.

밤 11시 16분에는 보호된 RAG 채팅 데모까지 들어갔다. 정상 HWPX는 검색되고 공격 HWPX는 격리되어 검색되지 않는 흐름이 실제로 연결됐다.

이쯤 되니 뭔가 진짜 제품 같아졌다.

### 7월 22일 — 기능을 발표로 바꾸는 밤

새벽에는 세 서비스의 응답과 지연된 리뷰 결과를 계속 맞췄다. 3시 25분에는 발표 자료가 저장소에 올라갔다.

기술적으로는 설명할 게 너무 많았다.

- HWPX ZIP/XML 보안 파서
- OpenDataLoader PDF와 PyMuPDF 정규화
- 의미 보존 diff
- 정적 규칙과 로컬 LLM
- 2차 감사
- SHA-256 감사 체인
- Git watcher
- MCP
- 승인 상태 머신
- 보호 RAG

문제는 이걸 다 설명하면 아무도 제품을 기억하지 못한다는 점이었다.

그래서 최종 메시지는 하나로 줄였다.

> 오염된 문서가 RAG의 지식이 되기 전에 막는다.

발표 데모도 정상 문서, 변조 문서, 위험 근거, 격리, 보호된 답변 순서로 압축했다. 대회 기간에는 공개 Streamlit 사이트도 배포했다. 심사위원이 README를 열었을 때 바로 실행할 수 있게 링크를 맨 위에 올렸다.

지금 생각하면 여기서 한 번 더 줄였어야 했다. 우리는 기술을 많이 지웠다고 생각했지만, 듣는 사람 입장에서는 아직 RAG, 임베딩, 리트리버, 인젝션, 격리 같은 단어가 한꺼번에 나왔다.

만든 사람에게는 당연한 단어가 처음 보는 사람에게는 전부 비용이다.

### 7월 23일 — 코엑스로 뛰어가다

발표 날에도 나는 랩미팅이 있었다.

오후 3시 47분에 끝났다. 팀 발표가 언제인지 다시 물어보고, 늦을 것 같다고 했다가 시간이 남았다는 답을 듣고 바로 출발했다.

근데 코엑스에서 그랜드볼룸 105호가 어디인지 몰랐다.

삼성역에서 내려 에스컬레이터 A 앞까지 간 다음 팀원에게 마중을 요청했다. 결국 발표 직전에 사람 같은 무언가를 발견해서 합류했다. 대회 후기에서 이런 말을 쓰는 게 좀 그렇지만, 다음에는 행사장 위치를 전날 확인하겠습니다.

발표는 10분, 질의응답은 5분이었다.

데모 영상의 소리가 나오지 않았고, 질문에서는 우리가 설명의 출발점을 잘못 잡았다는 게 드러났다. 우리는 RAG 문서 공급망과 색인 통제를 설명하고 있었는데, 듣는 입장에서는 “결국 파일 보안 아닌가”, “RAG와 일반 검색은 무엇이 다른가”부터 분명하지 않았다.

질문이 이상했다고 넘길 수도 있다. 근데 제품을 설명하는 쪽의 책임도 있다.

심사위원이 RAG를 이미 잘 안다는 전제로 발표를 만들었고, 그래서 “문서가 오염되면 왜 답변이 틀리는지”보다 아키텍처와 구현 완성도를 먼저 보여줬다. 우리가 가장 잘 만든 부분을 가장 이해하기 어려운 순서로 설명한 셈이다.

## 결과

결과 발표까지 기다렸지만 연락은 오지 않았다. 수상하지 못했다.

이번에는 아무것도 못 만들고 끝난 종류의 실패가 아니었다. 세 명이 역할을 명확히 나누었고, 실제 문서를 넣으면 분석하고, 위험한 문서는 격리하고, 승인된 문서만 RAG에 색인하는 데모까지 완성했다. 발표 자료와 공개 배포도 만들었다.

그러니까 더 아쉬웠다. 기술적으로 작동하는 제품을 만든 것과 심사위원에게 좋은 제품으로 이해시키는 것은 다른 문제였다. 아쉽긴 한데 뭐 어쩌겠음. 골든리트리버가 대세긴 하다.

## 잘한 점

### 분석 화면이 아니라 실제 색인을 막았다

가장 잘한 선택이다.

위험 점수 92점과 빨간 경고창만 보여줬다면 흔한 보안 대시보드가 됐을 것이다. IndexGuard는 공격 후보의 색인 청크를 0개로 만들고, 이전 안전 버전을 계속 검색하게 했다.

제품의 보안 주장을 코드와 상태로 증명했다.

### 역할을 서비스 경계로 나눴다

A, B, C는 발표용 이름이 아니라 실제 권한 경계였다.

- A만 원본 파일과 색인기에 접근한다.
- B는 정규화된 증거만 분석한다.
- C는 상태를 보여주고 명령만 요청한다.

이 구조 덕분에 AI가 공격 문서의 지시를 따라도 바로 색인을 승인할 수 없다. 기술적으로도 맞고, 세 명이 동시에 구현하기에도 좋았다.

### LLM에 최종 권한을 주지 않았다

AI 해커톤에서 LLM을 많이 쓰는 것 자체가 목표가 되기 쉽다.

우리는 반대로 AI가 의미를 해석하되 결정적 규칙과 정책 엔진이 최종 색인을 통제하게 했다. 숫자 변경이나 숨은 스크립트 같은 hard block은 LLM이 안전하다고 말해도 해제할 수 없다.

AI를 믿지 않아서 안 쓰는 게 아니라, 실패할 수 있다는 전제에서 썼다.

### 한컴 후원 맥락을 기능으로 연결했다

HWPX 지원은 장식이 아니었다. 실제 HWPX 텍스트와 표, 스타일, 숨김 흔적을 추출하고 PDF·DOCX와 같은 계약으로 넘겼다.

국내 공공·금융·기업 문서 환경이라는 시장 설명과도 자연스럽게 이어졌다.

## 오답노트

### 첫 30초가 너무 어려웠다

우리가 하고 싶은 말은 많았고 시간은 짧았다.

다음에는 첫 화면에서 아래 두 문장만 보여줄 것이다.

- 게이트 없음: 변조 문서가 색인되어 `월급 2,000만 원`으로 답함
- IndexGuard 적용: 변조 문서는 격리되고 기존 `월급 200만 원`으로 답함

그다음에야 왜 가능한지 설명해야 한다.

아키텍처는 증거지 도입부가 아니다.

### AI의 역할이 관객에게 선명하지 않았다

우리 설계에서는 AI가 최종 권한을 갖지 않는 것이 장점이었다. 하지만 AI 스타트업 해커톤 발표에서는 잘못 설명하면 “그럼 AI가 별로 필요 없는 것 아닌가”로 들릴 수 있다.

`규칙은 숫자와 숨김 요소를 잡고, AI는 정책 의미와 우회 표현을 해석한다`는 역할 차이를 실제 한 사례로 보여줬어야 했다.

### 사업 설명이 늦었다

구매자는 CISO, 보안팀, AI 플랫폼팀과 내부감사팀이다. 고객은 HWPX 문서가 많고 외부 SaaS로 문서를 보내기 어려운 공공·금융·법무·국방 조직이다. 도입 방식은 온프레미스 API나 문서 수집 파이프라인 플러그인이다.

이 설명이 발표 후반에 있었다.

심사위원은 기술을 이해한 뒤 시장성을 판단하는 게 아니라, 왜 누가 돈을 내는지 이해해야 기술을 들을 이유가 생긴다.

### 발표 환경을 너무 믿었다

영상 소리, 공개 서버, 행사장 네트워크, 발표 PC는 전부 실패할 수 있다.

다음에는 아래를 따로 준비할 것이다.

1. 소리 없이도 이해되는 60초 영상
2. 로컬 원클릭 데모
3. 공개 배포
4. 정지 화면만으로 설명 가능한 백업 슬라이드
5. 발표 PC에서 전날과 당일 각각 리허설

데모가 좋으면 하나로 충분한 게 아니라, 좋을수록 여러 형태로 복제해야 한다.

### 내가 발표 준비에 늦게 합류했다

랩미팅은 어쩔 수 있었지만 행사장 위치와 이동 시간은 미리 계산할 수 있었다.

개발을 끝까지 붙잡는 사람이 발표 직전까지 자리를 비우면 팀 전체의 리허설 시간이 줄어든다. 다음에는 기능 동결 시간을 더 앞당기고, 발표 날에는 발표 외 일정과 동선을 먼저 막아둘 것이다.

## 이번 대회에서 배운 것

좋은 기술을 만들면 알아서 알아봐 줄 거라는 생각은 위험하다.

해커톤에서 제품은 다음 네 번 완성돼야 한다.

1. 코드로 작동해야 한다.
2. 데모에서 재현돼야 한다.
3. 한 문장으로 이해돼야 한다.
4. 심사 기준의 언어로 가치가 설명돼야 한다.

우리는 1번과 2번은 꽤 잘했다. 3번도 표어까지는 만들었다. 그런데 4번에서 기술의 언어를 충분히 버리지 못했다.

또 하나 배운 건, 기능을 많이 만드는 속도보다 경계를 먼저 정하는 속도가 중요하다는 점이다. 이번에는 공통 계약과 권한을 일찍 고정한 덕분에 세 명이 동시에 움직일 수 있었다. 반대로 발표에서 무엇을 버릴지 정하는 속도는 늦었다.

코드는 합치면 되지만 설명은 그냥 합치면 길어진다.

## 앞으로

상을 못 탔다는 결과는 그대로다.

IndexGuard가 꽤 괜찮은 프로젝트였다는 생각도 그대로다. 두 문장은 충돌하지 않는다.

3명이 하루 만에 HWPX, PDF, DOCX를 분석하고, 정적 규칙과 로컬 LLM을 분리하고, 승인 상태 머신과 감사 체인을 만들고, 공격 문서가 실제 RAG 색인에 들어가지 않는 데모까지 완성했다.

다음에는 이 기술을 더 많이 보여주려고 하지 않을 것이다.

공격 문서 하나, 틀린 답변 하나, 차단 장면 하나, 정상 답변 하나.

그 네 장면을 먼저 보여주고 나머지는 질문을 받으면 설명하겠다.

아무튼 수상은 못했다. 근데 프로젝트는 남았다.
