## 글을 쓰며

7월 21일부터 23일까지 **CODEGATE 2026 AI 스타트업 해커톤**에 참가했다. 우리 팀은 RAG에 들어갈 문서를 검사하는 **IndexGuard**를 만들었다.

아이디어 정하고 역할 나눈 것부터 구현, 시연, 최종 발표와 결과까지 순서대로 적어 본다.

## 참가 동기와 아이디어 선정

대회 주제는 AI 스타트업이었고 한컴이 후원사로 참여했다. AI가 진짜 필요한 문제이면서, 국내 기업 문서 환경과도 이어지는 걸 만들고 싶었다.

RAG 보안 하면 보통 사용자 질문이나 모델 답변을 막는 쪽이 먼저 떠오른다. 우리는 그 앞 단계인 원본 문서를 봤다. 사내 문서가 변조된 채로 지식베이스에 들어가면 그 뒤 답변도 다 오염된다. 그래서 색인하기 전에 문서 변경을 검사하고 막는 게이트를 만들기로 했다.

## 팀 구성

팀원은 세 명이었다.

- [`caffeine-fighter`](https://github.com/caffeine-fighter)
- [`jwj7140`](https://github.com/jwj7140)
- [`AutoclickerI`](https://github.com/AutoclickerI)

나는 A, `jwj7140`은 B, `AutoclickerI`는 C를 맡았다.

| 담당 | 서비스 | 핵심 책임 |
|---|---|---|
| `caffeine-fighter` | A. 문서 수집·무결성·색인 게이트웨이 | 파일 감지, PDF·DOCX·HWPX 정규화, diff, 해시·버전 기록, 분석 요청, 색인 통제 |
| `jwj7140` | B. AI 위험 분석·감사 엔진 | sLLM 분석, 정책 의미 변경과 프롬프트 인젝션 탐지, 위험도·근거 산출, 고위험 재감사 |
| `AutoclickerI` | C. 운영 대시보드·승인 콘솔 | 변경 전후와 위험 근거 표시, 승인·보류·재분석, 보호된 RAG 시연 |

역할표만 보면 평범한데, 이번엔 각자 하지 말아야 할 것도 같이 정했다.

- A는 AI 위험도를 자체 계산하지 않는다.
- B는 원본 파일 저장소와 RAG 색인기에 접근하지 않는다.
- C는 위험도를 계산하거나 파일·색인을 직접 수정하지 않는다.

파일과 색인 권한을 가진 A가 위험도까지 스스로 판단하면 감사 구조가 무너진다. B가 공격 문서 속 지시문에 넘어가더라도 색인 권한이 없으니 피해가 제한된다. C는 운영자에게 증거와 할 수 있는 명령을 보여주기만 하고, 브라우저에서 상태를 새로 만들어내지 않는다. 이렇게 선을 그어 둔 덕에 세 명이 동시에 작업할 수 있었다.

## 무엇을 만들었나

우리가 만든 건 **IndexGuard**다. 표어는 "기억 전에, 검증."으로 정했다.

IndexGuard는 PDF, DOCX, HWPX 문서의 변경을 규칙과 AI로 분석해서, 숫자·정책 왜곡이나 간접 프롬프트 인젝션이 RAG 지식으로 저장되기 전에 막는 문서 무결성 게이트다.

지식베이스에 들어가는 문서 자체가 오염돼 있으면, 모델은 공격자가 바꾼 내용을 회사의 정상적인 지식으로 기억해 버린다. 예를 들면 이렇다.

| 원문과 변경문 | 판정 |
|---|---|
| `AutoclickerI 월급 2,000,000원` → `AutoclickerI의 월급 2,000,000원` | 의미가 같으므로 통과 |
| `2,000,000원` → `20,000,000원` | 금액 변조로 차단 |
| `월급` → `일급` | 지급 주기 변경으로 차단 |
| `AutoclickerI` → `jwj7140` | 적용 대상 변경으로 차단 |

글자 차이를 전부 막으면 오탐 많은 diff 도구가 될 뿐이다. 그렇다고 문장이 대충 비슷하다고 통과시키면 숫자, 단위, 사람 이름처럼 작은데 치명적인 변경을 놓친다. 그래서 결정적 diff와 정적 규칙으로 핵심 변경을 먼저 잡고, 정책 의미나 우회 표현 해석은 따로 떨어진 AI 서비스에 맡겼다.

판정과 실제 동작도 나눴다.

- 분석 판정: `ALLOW / REVIEW / BLOCK`
- 색인 동작: `INDEX / HOLD / QUARANTINE`

`BLOCK`이라고 빨간 글자를 띄우고 끝나는 게 아니다. 공격 문서는 실제 색인기에 들어가지 않고, 전에 승인된 안전한 문서가 그대로 남는다. 우리가 보여주고 싶었던 것도 위험해 보이는 화면보다는 **오염된 문서의 색인 청크가 0개**라는 결과였다.

### 왜 HWPX였나

한컴이 후원사라서 HWPX를 선택 기능이 아닌 P0로 잡았다.

발표 자료에 후원사 로고를 넣는 것보다는, 한컴이 실제로 많이 만나는 공공·기업 문서 환경을 제품 한가운데 두는 게 낫다고 봤다. HWPX를 많이 쓰는 조직은 문서를 외부 SaaS로 보내기 어렵고, 변경 이력과 승인 근거도 중요하게 본다. 온프레미스 RAG 보안 게이트라는 설명과 잘 맞았다.

HWPX는 ZIP과 XML 기반이라 본문만 읽는다고 끝나지 않는다. 비정상 압축, 외부 관계, 스크립트 payload, OLE, 숨김 스타일 같은 입력은 분석기 자체를 공격할 수 있다. 그래서 파일 형식과 ZIP 구조부터 검사하고, 본문·표·스타일과 숨김 흔적을 뽑았다. 중간에 문제가 생기면 텍스트만 대충 읽고 통과시키지 않고 실패 상태로 남겼다.

레거시 바이너리 HWP는 넣지 않았다. 24시간 안에 HWPX 하나를 제대로 끝내고 PDF, DOCX를 같은 파이프라인에 붙이는 쪽을 골랐는데, 지금 봐도 잘한 판단 같다.

## 대회 중 경과

### 첫날 — 일단 계약부터 고정했다

전날 침대에서 기절했다가 오전 7시에 눈을 떴다. 행사장에는 8시 41분쯤 도착했다.

처음엔 코드를 치지 않고 제품을 한 문장으로 뭐라고 할지, 최종 데모는 어떻게 할지, 공통 JSON은 어떻게 생길지부터 정했다. 기능을 많이 만드는 게 목표가 아니었다. 데모 흐름은 이랬다.

1. 정상 HWPX가 RAG에 들어가 있다.
2. 공격자가 숫자와 정책을 바꾸고 숨은 지시문을 넣는다.
3. IndexGuard가 변경 구간과 위험 근거를 찾는다.
4. 위험 문서를 격리해 실제 색인을 막는다.
5. 게이트가 없는 RAG와 보호된 RAG의 답변을 비교한다.

이 흐름에 안 걸리는 기능은 만들지 않기로 했다.

오전 10시 43분쯤 팀 방향과 역할을 채팅방에 올렸고, 11시 32분에 [IndexGuard 저장소](https://github.com/Generated-by-AI/IndexGuard)를 열었다. 11시 30분대에 전략 문서가 들어갔고, 12시 33분에 첫 문서 무결성 게이트웨이가 올라갔다. 오후 3시 22분에는 A 게이트웨이에 Git diff watcher가 붙었다.

그동안 `jwj7140`은 B 분석 경로와 OpenAI 호환 로컬 모델 연결을 만들었고, `AutoclickerI`는 대시보드와 운영자 명령 흐름을 구현했다.

저녁부터는 각자 만든 걸 `main`에 계속 합쳤다. 충돌이 없으면 그냥 push하고 merge했고, 계약이 어긋나는 부분만 바로 고쳤다. 막상 붙여 보니 문제가 계속 나왔다.

- A와 B가 같은 `decision`을 서로 다른 의미로 사용함
- `ALLOW` 판정과 실제 `INDEX` 완료를 같은 사건처럼 표시함
- 재분석 결과가 이전 후보 문서의 SHA와 섞일 수 있음
- C가 화면에서 권위 있는 상태를 다시 계산함
- B가 죽었을 때 문서가 애매한 상태로 남음

그래서 `ALLOW + INDEX`가 나와도 운영자가 승인하기 전까지는 `HOLD`로 두고, 승인 시점의 후보 SHA-256이 현재 문서와 같을 때만 색인하게 했다. B가 죽거나 계약에 안 맞는 응답을 보내면 자동으로 통과시키지 않는다. 보안 제품이니까 실패하면 편하게 넘어가기보다 멈추는 쪽을 택했다.

### 첫날 밤 — 배관이 터졌다

첫날 밤 11시 44분쯤 집에 급한 일이 생겼다. 배관이 터졌다. 응급처치를 못 하면 물바다가 되는 종류였다.

집에 가서 해결하고 다시 나오니 막차가 끊겨 있었다. 택시를 탈까 하다가 27분 뒤에 차가 있다는 걸 알았는데, 결국 그것도 놓치고 다음 N61을 탔다.

지하철에서는 작업하기 힘들어도 버스에서는 뭐라도 할 수 있었다. 이동하면서 팀 상황을 확인했고, 새벽 2시 25분쯤 방배역을 지나 다시 합류했다.

해커톤 후기에 배관 얘기를 길게 쓸 건 아닌데, 그때 작업 상태를 설명하려면 빼기가 어렵다. 기능 통합하고 발표 준비하는 와중에 집이 물바다가 될 뻔했다. 어쨌든 해결하고 행사장으로 돌아와서 작업을 이어 갔다.

### 둘째 날 — 작동하는 코드를 시연으로 바꿨다

새벽에는 세 서비스 사이의 계약과 늦게 도착하는 분석 결과를 계속 맞췄다. 오전에는 시연 영상을 찍었다.

첫 번째 영상에서는 정작 보여줘야 할 부분이 거의 안 보였다. 그래서 다시 찍었다. 제품이 실제로 돌아가는 것과 영상에서 돌아가는 것처럼 보이는 건 또 다른 문제였다.

최종 데모는 이렇게 줄였다.

1. 정상 HWPX의 정책 답변 확인
2. 숫자와 숨은 지시문이 변조된 HWPX 투입
3. 숫자 diff와 프롬프트 인젝션 근거 표시
4. `BLOCK / QUARANTINE` 판정
5. 공격 문서의 색인 청크가 0개임을 확인
6. 기존 안전 문서로 정상 답변 유지

대회 기간에 Streamlit 운영 콘솔도 공개 배포했다. README 첫 화면에는 실행 링크, 핵심 시나리오, 기술 스택을 올렸다.

기술적으로 할 얘기는 많았다.

- HWPX ZIP/XML 보안 파서
- OpenDataLoader PDF와 PyMuPDF 정규화
- 의미 보존 diff
- 정적 규칙과 로컬 sLLM
- 고위험 2차 감사
- SHA-256 감사 체인
- Git watcher
- MCP
- 승인 상태 머신
- 보호된 RAG

문제는 이걸 다 설명하면 아무도 제품을 기억 못 한다는 거였다. 그래서 표어를 “기억 전에, 검증.”으로 줄였다. 지금 생각하면 발표도 그만큼 더 줄였어야 했다.

### 발표 날 — 데모데이

발표 날은 오후 2시 24분에 슬슬 일어났다.

4시 10분쯤 맞춰 가려고 했고, 실제로는 4시 17분에 코엑스 그랜드볼룸 앞에 도착했다. 발표 10분, 질의응답 5분이었고, 입장하는 순간부터 시간이 간다는 설명을 듣고 팀에 전달했다.

`jwj7140`은 이미 발표 대기 중이었다. `AutoclickerI`는 랩미팅이 늦게 끝나서 삼성역에서 코엑스 안으로 뛰어오는 중이었다. 에스컬레이터 A 앞에 있다고 해서 내가 마중을 나갔다. 코엑스에서 사람 찾는 게 생각보다 쉽지 않았는데, 4시 38분쯤 겨우 만났다.

발표는 준비한 흐름대로 했다. 그런데 영상 소리가 안 나왔다.

우리는 화면만 봐도 내용이 보인다고 생각했지만, 발표장에서 소리가 빠지면 관객은 영상 속도나 어디가 중요한지 따라가기 어렵다. 만들 때는 두 번이나 찍어 놓고 재생 환경 확인은 놓쳤다.

질의응답에서는 "RAG 보안이라기보다 파일 보안 아닌가", "RAG와 일반 검색은 어떻게 다른가"에 가까운 질문을 받았다.

처음엔 우리가 만든 게 딱 그 교집합이라고 생각했다. 파일 변경을 검사하긴 하지만 목적은 RAG 색인 오염을 막는 거니까.

그런데 다시 생각해 보면, 문제가 어디서 시작되는지를 우리가 충분히 쉽게 설명하지 못했다는 얘기이기도 했다. 심사위원이 RAG, 임베딩, 리트리버를 이미 안다고 깔고 발표했다. 그래서 오염된 문서가 어떻게 틀린 답변을 만드는지보다 아키텍처와 보안 구조를 먼저 꺼냈다. 만든 사람한테는 당연한 단어도 처음 듣는 사람한테는 하나하나가 부담이다.

## 결과

발표가 끝나고 결과를 기다렸지만 따로 연락은 오지 않았다.

개인적으로는 수상권이었다고 생각한다. HWPX 지원, 처음부터 끝까지 이어지는 차단 데모, 공개 배포, 발표 자료까지 다 끝냈다. 심사표가 공개되지 않았으니 어디까지나 내 느낌이다. 그래도 상을 못 받았다고 제품까지 깎아내리고 싶지는 않다.

다만 잘 만든 것과 잘 보여준 건 달랐다. 다음에 고칠 건 꽤 분명하다.

## 오답노트

### 도입부가 어려웠다

하고 싶은 말은 많았고 발표 시간은 짧았다.

다음에는 첫 화면에 이 두 줄부터 띄울 생각이다.

- 게이트 없음: 변조 문서가 색인되어 `월급 2,000만 원`으로 답함
- IndexGuard 적용: 변조 문서는 격리되고 기존 `월급 200만 원`으로 답함

왜 이게 되는지는 그다음에 설명하면 된다. 아키텍처는 제품을 먼저 보여준 뒤 근거로 꺼내는 게 나았다.

### AI의 역할이 선명하지 않았다

우리 설계에서는 AI가 최종 권한을 갖지 않는 게 장점이었다. 그런데 AI 스타트업 해커톤에서 이걸 잘못 설명하면 "그럼 AI는 왜 필요한데?"로 들릴 수 있다.

규칙은 숫자와 숨김 요소를 잡고, AI는 정책 의미와 우회 표현을 해석한다. 이 차이를 사례 하나로 나란히 보여줬어야 했다.

### 사업 설명이 늦었다

살 사람은 보안팀, AI 플랫폼팀, 내부감사팀이다. 대상은 HWPX 문서가 많고 외부 SaaS로 문서를 보내기 어려운 공공·금융·법무 조직이고, 도입은 온프레미스 API나 문서 수집 파이프라인 플러그인 형태다.

이 얘기를 발표 후반에 했는데, 처음에 했어야 했다. 심사위원 입장에서는 누가 왜 돈을 내는지 알아야 기술 설명을 들을 이유가 생긴다.

### 발표 환경을 믿었다

영상 소리, 행사장 네트워크, 공개 서버, 발표 PC 전부 실패할 수 있다. 다음에는 이런 걸 따로 준비해 두려고 한다.

1. 소리 없이도 이해되는 60초 영상
2. 로컬 원클릭 데모
3. 공개 배포
4. 정지 화면만으로 설명 가능한 백업 슬라이드
5. 발표 PC에서의 실제 재생 테스트

데모가 좋으면 좋을수록 여러 벌로 준비해 둬야 한다.

## 잘한 점

### 실제 색인을 막았다

제일 잘한 선택이다. 위험 점수 92점에 빨간 경고창만 띄웠다면 흔한 분석 대시보드였을 거다. IndexGuard는 공격 후보의 색인 청크를 실제로 0개로 만들고, 이전 안전 버전이 계속 검색되게 했다. 화면이 아니라 시스템 상태로 보여줄 수 있었다.

### 권한을 분리했다

A, B, C는 발표용 이름이 아니라 실제 서비스 경계였다.

B의 AI가 공격 문서 속 지시문을 따르더라도 파일이나 색인은 못 바꾼다. C가 화면 상태를 잘못 만들어도 승인 요청 이상은 할 수 없다. 최종 색인은 A가 문서 SHA와 승인 상태를 다시 확인한 다음에 실행한다. AI가 틀려도 안전하게 버티는 쪽으로 만들었다.

### 한컴 후원 맥락을 기능으로 연결했다

HWPX를 구색으로 넣은 게 아니다. 실제 HWPX 본문, 표, 스타일, 숨김 흔적을 뽑아서 PDF·DOCX와 같은 계약으로 넘겼고, 국내 공공·금융·기업 문서 환경이라는 시장 설명과도 자연스럽게 이어졌다.

### 계약을 먼저 정했다

세 명이 동시에 작업하면서도 처음부터 끝까지 연결할 수 있었던 건 이것 덕분이다. 각자 코드부터 짰다면 `decision`, `index_action`, 문서 버전과 SHA의 의미를 맞추느라 시간을 다 썼을 거다. 공통 JSON과 권한 경계를 먼저 박아 둬서 merge가 빨랐다.

## 앞으로

이번 대회를 하면서, 해커톤 제품은 이 네 가지를 다 갖춰야 한다고 느꼈다.

1. 코드로 작동해야 한다.
2. 데모에서 재현돼야 한다.
3. 한 문장으로 이해돼야 한다.
4. 심사 기준의 언어로 가치가 설명돼야 한다.

이번엔 1번, 2번은 꽤 잘했고 3번도 표어까지는 만들었다. 4번에서는 기술 용어를 더 덜어낼 수 있었다.

공통 계약과 권한은 일찍 정해서 세 명이 같이 움직일 수 있었는데, 발표에서 뭘 뺄지는 늦게 정했다. 코드는 합치면 되지만 발표는 각자 설명을 합친다고 정리되지 않았다.

`jwj7140`은 로컬 모델과 B 분석 엔진을 실제 서비스로 만들었고, `AutoclickerI`는 복잡한 상태와 근거를 운영자가 다룰 수 있는 화면과 RAG 데모로 바꿨다. 나는 문서가 들어오는 순간부터 승인된 SHA만 색인되는 마지막 단계까지 A 게이트웨이와 전체 계약을 이었다. 셋 중 한 명이라도 자기 몫을 못 끝냈으면 최종 데모는 안 나왔다.

다음엔 기술을 더 많이 보여주려고 하지 않을 거다. 공격 문서 하나, 틀린 답변 하나, 차단되는 모습 하나, 정상 답변 하나. 이 넷부터 보여주고 나머지는 질문이 오면 설명하겠다.
